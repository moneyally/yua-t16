# DESIGN.md — ORBIT-DR1: 상태 고정 델타룰 헤드

버전 1.1 (2026-09-11). 이 문서는 SSOT다. RTL·골든 모델·테스트가 이 문서와 다르면 문서를 먼저 고친다.

## 1. 한 문단 요약

ORBIT-DR1은 **delta-rule 기반 순환 상태 메커니즘**(Gated DeltaNet 및 관련 fast-weight 구조)의
**헤드 하나**를 하드웨어로 구현한다.[^kda]

[^kda]: Kimi Delta Attention 은 **채널별(per-channel) 감쇠**를 쓴다 — 2절의 스칼라 α 와 다르다.
    RWKV-7 도 감쇠 항의 위치와 형태가 다르다. "계열" 로 묶지 않고, v1 은 2절 식 하나로 고정한다
    (9절 위험 항목).
d×d 상태 행렬 S를 온칩 SRAM에 상주시키고, 토큰마다 (1) 감쇠, (2) 랭크-1 외적 갱신, (3) 상태-벡터 곱 읽기를 수행한다.
기존 `mac_array`(출력 고정 외적 누산)가 (2)의 핵심이며, 기존 제어 평면(디스크립터 큐, IRQ, 트레이스)이 호스트 인터페이스다.
**선행 연구가 있다.** Gupta, Wang, Kannan, Prasanna, *A Persistent-State Dataflow Accelerator for
Memory-Bound Linear Attention Decode on FPGA*, arXiv **2603.05931** (2026-03).
Gated DeltaNet 의 **2MB 순환 상태를 Alveo U55C 의 온칩 BRAM 에 상주**시켜 메모리 바운드를
컴퓨트 바운드로 바꾼다. Vitis HLS, 300MHz, **63 µs/token**, H100 PCIe 대비 4.5배,
온칩 9.96W 로 토큰당 에너지 효율 최대 60배.

DR1 은 이것을 **기준선**으로 두고, 차이를 이렇게 정의한다:

| | 2603.05931 | DR1 |
|---|---|---|
| 구현 | Vitis HLS, **5단계 파이프라인** | **손으로 쓴 SystemVerilog RTL**, 직렬 FSM |
| 수치 형식 | FP32 (2MB/32헤드/d=128 → 원소당 4B 에서 **추정**) | **Q1.15 고정소수, 결정론적** |
| **토큰당 상태 패스** | **읽기 1 + 쓰기 1** | **3패스 — DR1 이 더 나쁘다** (9절) |
| 헤드 병렬 | Grouped Value Attention, 이터레이션당 2~16 value-head | 헤드 1개 |
| 검증 | — | **비트 정확 골든 모델과 전 토큰 비교** (7절) |
| 제어 평면 | HLS 생성 | **기존 디스크립터 큐·IRQ·트레이스 IP 재사용** |
| 규모 | d=128, 32헤드 | **d=16 부터** (4절) |

**최초라는 주장은 하지 않는다.** 전체 선행 연구 목록과 사양 비교는 `docs/PRIOR_ART.md`.

> 각주: 패스 수·파이프라인 단계·GVA·상태 규모는 **정원이 arXiv 초록을 직접 확인**해 준 값이다
> (2026-09-11). 수치 형식만 **추정**이다 — 초록이 명시하지 않았고, 2MB ÷ (32 × 128 × 128) = 4바이트에서
> 유도했다. 논문 **본문은 못 읽었다** (이 환경에서 arxiv.org 가 egress 프록시에 막힌다).
> 출처 등급은 `docs/PRIOR_ART.md` 0절, 검색 질의문은 `docs/LOG.md` 세션 10 — `CLAUDE.md` 규칙 7.

## 2. 수학 (골든 모델의 정의)

토큰 t마다 입력 q_t, k_t, v_t ∈ R^d, 게이트 α_t ∈ [0,1], 학습률 β_t ∈ [0,1].
(α, β 는 UQ1.15 로 표현한다 — 3절. 1.0 이 정확히 들어간다.)

```
S_t = α_t · S_{t-1} · (I − β_t · k_t · k_tᵀ) + β_t · v_t · k_tᵀ      # 상태 갱신
o_t = S_t · q_t                                                    # 출력
```

하드웨어 친화형 전개 (**같은 결과**, 연산 순서만 고정):

```
p     = S_{t-1} · k_t                 # d×d · d  → d      (상태 읽기 1회)
err   = v_t − α_t · p                 # d                 (α 를 곱한 p 를 뺀다)
S_t   = α_t · S_{t-1} + β_t · err · k_tᵀ   # 스케일 + 외적 누산 (mac_array)
o_t   = S_t · q_t                     # 상태 읽기 1회
```

이 전개는 위 정의식과 **모든 α 에 대해 정확히 같다**:

```
α·S + β·(v − α·p)·kᵀ = α·S + β·v·kᵀ − α·β·p·kᵀ = α·S·(I − β·k·kᵀ) + β·v·kᵀ
```

`err = v − p` (α 없이)는 α=1 일 때만 같다. 쓰지 않는다.
골든 모델(`sim/golden/deltarule.py`)이 이 식이고, RTL 은 그것과 비트 단위로 일치해야 한다.

## 3. 숫자 형식 (v1은 고정소수점, 결정적)

- v1: **Q1.15 고정소수점** (16비트, 부호 1 + 소수 15). 곱은 32비트(Q2.30), 누산은 40비트, 상태 저장은 Q1.15로 재양자화(반올림 방식: round-half-to-even 고정).
- **두 가지 형식을 쓴다** (2026-09-11 결정):

  | 형식 | 폭 | 범위 | 쓰는 곳 |
  |---|---|---|---|
  | **Q1.15** (부호 있음) | 16b | [-1.0, +0.999969...] | `S`, `q`, `k`, `v`, `p`, `err`, `o` |
  | **UQ1.15** (부호 없음) | 16b | [0, 2) — **0x8000 = 1.0 정확** | `α`, `β` **만** |

  부호 있는 Q1.15 에는 **1.0 이 없다** (최대 32767/32768 = 0.999969...). 그런데 2절의 α, β ∈ (0,1] 은 1 을 포함한다. α, β 는 정의상 음수가 아니므로 **부호 비트를 버리고 UQ1.15 로 두면 같은 16비트로 1.0 을 정확히 얻는다.** 특별 해석이 아니라 형식 그대로다.
  하드웨어에서는 "부호 있는 Q1.15 × 부호 없는 UQ1.15" 곱셈(17비트 부호 확장)으로 처리한다.
  **1.0 초과는 미정의**다 — 골든 모델은 `ValueError`, RTL 은 `0x8000` 으로 클램프하고 트레이스에 `CLAMP_EVENT` 를 남긴다. 상세는 `spec/deltarule.md`.
- **`α·S` 와 `β·err·kᵀ` 는 Q2.30 누산기에서 합산한 뒤 1회만 재양자화한다.** 항마다 Q1.15 로 내렸다가 더하면 재양자화가 2번 일어나 오차가 1 LSB 를 넘는다(실측 1.06~1.08 LSB → 1회 재양자화 시 0.63~0.66 LSB). 이 순서는 8절의 `mac_array` 재사용 계획("acc 초기값을 α·S 행으로 로드")과 같다.
- 이유: 합성 가능, 결정적, 골든 모델과 비트 일치 검증이 쉬움. BF16은 v2.
- 골든 모델(`sim/golden/deltarule.py`)은 numpy int 연산으로 같은 반올림을 구현한다. float로 만든 뒤 변환하지 않는다.
- 오버플로 정책: 포화(saturate). 트레이스 링에 `SAT_EVENT` 기록.

## 4. 크기

| 파라미터 | v1 (시뮬/KV260) | v2 (Alveo) |
|---|---|---|
| d (헤드 차원) | 16 → 64 | 128 |
| 상태 S | 16×16 → 64×64 Q1.15 (8KB) | 128×128 Q1.15 또는 BF16 (32~64KB) |
| 동시 세션 수 | 1 | 4~16 (세션 = 상태 슬롯) |
| 토큰당 목표 사이클 | ≤ 4·d (64: ≤256) | ≤ 2·d |

v1은 **d=16으로 먼저 끝낸다** (기존 mac_array 그대로). 16에서 골든 일치 → 64로 확장. 64가 안 되면 16으로 끝낸 것을 성과로 보고한다.

## 5. 블록 구조

```
host (tools/ Python HAL, driver/)
  │  MMIO + descriptor (기존 reg_top / desc_queue / desc_fsm_v2)
  ▼
dr1_top  ── opcode DELTA_STEP / DELTA_INIT / DELTA_DUMP
  ├── state_sram      d×d Q1.15, 2R1W 또는 뱅크 분할 (v1: 단순 1R1W + 직렬)
  ├── matvec_unit     p = S·k, o = S·q      (행 단위 순회, d 사이클)
  ├── mac_array       S += β·err·kᵀ 외적 누산 (기존 모듈, acc를 상태와 결합)
  ├── scale_unit      S ← α·S  (행 단위 곱, matvec와 파이프라인 공유 가능)
  ├── vec_regs        q, k, v, err (각 d×16bit)
  └── perf/trace      토큰당 사이클, 포화 이벤트 → 기존 trace_ring
```

디스크립터(64B, 기존 `spec/descriptor.md` 확장):
- `DELTA_INIT {slot}` : 상태 슬롯을 0으로.
- `DELTA_STEP {slot, q_addr, k_addr, v_addr, o_addr, alpha_q15, beta_q15}` : 한 토큰 처리. 완료 시 IRQ.
- `DELTA_DUMP {slot, dst_addr}` : 상태 전체를 메모리로 (검증용).

## 5.1 완료 신호 계약 (버전 0.2 추가, 2026-09-11)

`done_pulse` 하나로 "끝났다"를 표현하면 **성공과 실패를 구분할 수 없다.**
실제로 G2 제어 평면에서 이 때문에 버그가 났다: fault 난 디스크립터가
완료 IRQ(`DESC_DONE`)를 올렸다 (`docs/BUGS.md` BUG-001). 원인은
`desc_fsm_v2` 의 FSM 이 `ST_FAULT → ST_DONE` 으로 가고 `ST_DONE` 이 진입 경로를
구분하지 않고 `done_pulse` 를 내는 것이었다.

**따라서 완료 신호는 세 개로 분리한다.** DR1 과 앞으로 만드는 모든 FSM 은 이 계약을 따른다.

| 신호 | 의미 | 폭 | 언제 |
|---|---|---|---|
| `done_ok` | **성공** 완료 | 정확히 1사이클 | 상태 쓰기가 끝난 다음 사이클 |
| `done_err` | **실패** 종료 | 정확히 1사이클 | fault 확정 다음 사이클 |
| `done_pulse` | **리타이어** (= `done_ok \| done_err`) | 정확히 1사이클 | 위 둘 중 하나가 날 때 |

규칙:

1. **한 트랜잭션은 `done_ok` 와 `done_err` 중 정확히 하나만 낸다.** 둘 다 내거나 둘 다 안 내면 버그다.
2. **세 신호 모두 폭은 정확히 1사이클이다.** 레벨이 아니다.
3. **완료 IRQ 는 `done_ok` 에만 걸린다.** 실패는 별도 fault IRQ 로 보고한다.
4. **자원 회수(OOM 사용량 감소, 큐 슬롯 반납)는 `done_pulse`(리타이어)에 걸린다.**
   성공만 회수하면 실패 트랜잭션마다 누수가 생긴다.
5. **`done_ok` 는 "상태 쓰기 완료 후 1사이클"이다.** `DELTA_STEP` 에서는 S 와 o_t 가
   모두 메모리에 쓰인 다음 사이클을 뜻한다. 파형(GTKWave)으로 직접 확인한다.

기존 G2 모듈은 하위 호환을 위해 `done_pulse` 이름을 리타이어 의미로 유지하고
`done_ok` / `done_err` 를 추가한다. 새 모듈은 세 개를 처음부터 낸다.

v1의 데이터 경로는 기존 `act_sram`/`wgt_sram`처럼 **온칩 SRAM 스크래치**에서 q/k/v를 읽는다. DDR/PCIe는 v1 범위 밖이다. 호스트는 MMIO로 스크래치를 채운다(느려도 됨).

### 6.1 실측 (d=16, RTL) — W7·W8

**추정과 실측을 섞지 않는다.** 아래는 `tb/` 가 실제로 센 값이다.

| 모듈 / 명령 | 골든 함수 | 계약 상한 | **실측 (d=16)** | 출처 |
|---|---|---|---|---|
| `matvec_unit` | `matvec()` | D+4 = 20 | **19** (= D+3) | `tb/tb_matvec_unit.py` M4 |
| `update_unit` (행 1개) | `update_row()` | D+6 = 22 | **2** (D 와 무관) | `tb/tb_update_unit.py` U5 |
| `err_unit` | `compute_err()` | — | **조합 1사이클** | `tb/tb_err_unit.py` E4 |
| `dr1_top` `DELTA_INIT` | — | — | **19** | `tb/tb_dr1_top_fsm.py` F1 |
| `dr1_top` `DELTA_STEP` | `step()` | **4·d = 64** | **126** ← 여전히 초과 | `tb/tb_dr1_harness_rtl.py` R8 (1,000토큰 전부 126) |
| `dr1_top` `DELTA_DUMP` | — | — | **305** | `tb/tb_dr1_top_fsm.py` F2 |
| `dr1_top` `DELTA_STEP` **(d=64)** | `step()` | 4·d = 256 | **462** ← 초과 | `tb/tb_dr1_d64.py` X4. 20토큰 비트 일치 |
| `DELTA_STEP` — **호스트 경로**(디스크립터) | `step()` | — | **127** | `tb/tb_dr1_host_e2e.py` H2, `tb/tb_dr1_soc_top.py` S3 |

**126 과 127 의 차이**: 126 은 `dr1_top` 의 `cmd_valid` 부터 `done` 까지다. 127 은
호스트가 `DR1_CYCLES` 로 읽는 값이고, 디스크립터 디스패치 1사이클이 더 들어 있다.
**AXI4-Lite 를 지나도 127 그대로다** (`tb_dr1_soc_top.py` S3 = `tb_dr1_host_e2e.py` H2).
버스가 사이클 수를 바꾸지 않는다는 뜻이다 — 바뀌면 그게 버그다.

`matvec_unit` 이 D+3 인 이유: `state_sram` 읽기 지연 1사이클 때문에 요청과 소비가
한 사이클 겹쳐서 D행을 D+1 사이클에 처리하고, 거기에 start 수락 1 + done 1 이 붙는다.

`update_unit` 이 D 와 무관하게 2사이클인 이유는 **열 방향을 D개 PE 로 펼쳤고**(8.1절),
갱신의 항이 정확히 2개라 `mac_pe` 를 **DUAL 모드**로 한 사이클에 둘 다 넣기 때문이다.

#### 6.2 `DELTA_STEP` 126 사이클의 내역

| 단계 | 사이클 | 무엇 |
|---|---|---|
| 명령 수락 | 1 | |
| `ST_LOAD_K` | 18 | **k 만** 적재한다 (d + 2). p = S·k 에 즉시 필요 |
| `ST_MV_K` | 20 | p = S·k. **이 동안 v 를 겹쳐서 적재한다** (18 < 20 이라 완전히 숨는다) |
| `ST_ERR` | 1 | err = v − α·p (조합) |

| `ST_MV_Q` | 20 | o = S_next·q |
| `ST_WR_O` | 16 | o 를 스크래치에 1개/사이클 |
| 완료 | 1 | |
| **합계** | **126** | 계약 상한 64 의 **2.0배** |

#### 6.3 205 → 126 으로 줄인 방법과, 남은 거리

W7 최초 구현은 **205 사이클**이었다. 두 가지를 고쳐 126 이 됐다
(**두 번 다 1,000토큰 비트 일치를 유지하는지 먼저 확인했다**):

| 고친 것 | 전 | 후 | 방법 |
|---|---|---|---|
| 피연산자 적재 | 50 | **18** | q,k,v 를 순서대로 다 읽던 것을, **k 만 기다리고 v·q 는 계산과 겹쳐서** 적재. 스크래치 포트가 `ST_MV_K`/`ST_UPD_*` 동안 놀고 있었다 |
| 행 갱신 | 96 | **49** | `mac_pe` 에 **DUAL 모드**(한 사이클에 곱 2개) 추가 → `update_unit` 4→2 사이클. 그리고 `dr1_top` 이 **다음 행을 미리 읽어** 행당 6→3 사이클 |

**남은 것과 그 성격** (아직 안 함, 추정):

| 항목 | 사이클 | 줄일 수 있나 |
|---|---|---|
| `ST_MV_K` + `ST_MV_Q` | 40 | **구조적 하한이다.** 1R1W SRAM 에서 d행을 읽으면 d+3 이다 |
| `ST_UPD_*` | 49 | 3→2사이클/행 가능 (requant 단계를 다음 행 MAC 과 파이프라인) → **33** |
| `ST_LOAD_K` + `ST_WR_O` | 34 | 스크래치를 128비트로 넓히면 → **약 6**. 다만 호스트 MMIO 창과 BRAM 추론을 다시 봐야 한다 |

셋 다 하면 **약 80** 이다. 계약 64 는 **피연산자 이동을 세지 않은 숫자**이므로
그때 가서 계약 쪽을 고칠지(= 이동 비용을 명시적으로 넣을지) 정한다.
**지금 고치지 않는다** — 못 맞춘 숫자를 지우면 계약이 사라진다.

#### 6.4 d=64 (2026-09-11 확인)

**같은 RTL 을 파라미터만 바꿔** 돌렸다 (`PARAM_D=64 PARAM_SCRATCH=8192`).
파일을 복제하지 않았다 — 복제하면 한쪽만 고치는 날이 온다.

| | d=16 | d=64 | 비 |
|---|---|---|---|
| `DELTA_STEP` 사이클 | 126 | **462** | 3.7배 |
| 계약 상한 (4·d) | 64 | 256 | |
| 초과 배수 | 2.0× | **1.8×** | d 가 커질수록 **가까워진다** |

d 가 커질수록 비율이 좋아지는 이유: 고정 오버헤드(명령 수락, ERR, 완료)는 그대로이고
d 에 비례하는 단계가 지배하기 때문이다. 즉 **구조가 d 에 대해 선형**이다.

골든과 **20토큰 비트 일치**를 확인했다 (`tb/tb_dr1_d64.py` X3). 1,000토큰은
파이썬 골든이 d² 라서 d=16 쪽에서 본다.

**주의**: `g2_ctrl_top` 통합 빌드는 **d=16 그대로**다. d=64 는 면적이 약 4배라
KV260 급에 들어갈지 모른다 (`docs/FPGA.md` — Vivado 미측정). d=64 는 지금
**시뮬레이션에서 맞다는 것까지** 확인한 상태다.

100MHz FPGA에서 토큰당 ≈ 2.1µs/헤드. 느리다. **v1의 목적은 속도가 아니라 "상태가 칩을 떠나지 않는 정확한 갱신"의 증명**이다.

## 7. 검증 계약

모든 테스트는 다음 순서를 따른다:
1. `sim/golden/deltarule.py`로 무작위 시드 N 토큰 시퀀스의 S_t, o_t 생성 (Q1.15 정수 연산).
2. cocotb가 같은 입력을 RTL에 넣고 `DELTA_DUMP`로 상태를 꺼내 **비트 단위 비교**.
3. 불일치 시 첫 불일치 토큰 인덱스, 행, 열, 기대/실제 값을 출력.

불변조건 (매 테스트 마지막에 검사):
- I1. `DELTA_INIT` 후 상태는 전부 0.
- I2. α=1, β=0이면 상태는 변하지 않는다.
- I3. β=0이면 o_t = S_{t-1}·q_t 와 일치.
- I4. 포화가 일어난 토큰 수 == 트레이스 링의 `SAT_EVENT` 수.
- I5. 같은 입력·같은 시드 → 두 번 실행 결과 동일 (결정성).
- I6. **완료 신호 계약 (5.1절)**: 한 트랜잭션에 `done_ok` 와 `done_err` 중 정확히 하나만,
  폭 1사이클로 발생한다. fault 트랜잭션은 `done_ok` 를 내지 않는다.
  잘못된 디스크립터를 주입해 이것을 직접 검사한다 (`tb/tb_g2_ctrl_top_fault_irq.py` 패턴).

합성 게이트: `yosys synth -top dr1_top` 통과, `verilator --lint-only -Wall` 경고 0 (의도된 UNUSED 제외).

### 8.1 `update_unit` 이 `mac_pe` 를 쓰는 방식 (W6 결정 기록)

문제: `mac_pe` 는 INT8×INT8 → 32비트다. DR1 은 Q1.15 이고 α 는 UQ1.15 라
**0x8000(=1.0)이 부호 있는 16비트에 안 들어간다.**

선택지와 결정:

| 안 | 내용 | 판정 |
|---|---|---|
| (a) | `mac_pe` 에 폭 파라미터(`A_W`/`B_W`/`ACC_W`) 추가, 기본값은 8/8/32 그대로 | **채택** |
| (b) | DR1 전용 MAC 셀을 새로 쓴다 | 기각 — CLAUDE.md 0절 "새로 만들지 말고 진화시킨다" |
| (c) | α 를 32767 로 근사해서 기존 셀을 그대로 쓴다 | 기각 — 1.0 이 표현 안 되면 UQ1.15 를 도입한 이유가 사라진다 |

**W7 추가**: 갱신의 항이 정확히 2개(`α·S[j]` + `berr·k[j]`)라 누산기를 두 사이클
돌릴 이유가 없었다. `mac_pe` 에 **`DUAL` 파라미터**를 넣어 한 사이클에 곱 두 개를
누산하게 했다. `DUAL=0`(기본)이면 두 번째 곱셈기는 **generate 로 아예 안 만든다** —
`mac_array` 는 그대로다.

(a) 의 위험은 **기존 `mac_array` 회귀**다. 그래서 기본값을 예전과 똑같이 두고
(`mac_array` 는 파라미터를 주지 않는다) **셀 수로 확인했다**:

| 모듈 | W5 (변경 전) | W6 (변경 후) |
|---|---|---|
| `mac_pe` | 730 | 730 |
| `mac_array` | 196,352 | 196,352 |

`update_unit` 은 `mac_pe #(.A_W(17), .B_W(16), .ACC_W(40))` 를 **D개** 인스턴스화한다
(열 하나당 하나). α 는 `{1'b0, alpha_uq15}` 로 부호 있는 17비트가 된다.

사용 안 함 (격리): `rtl/behavioral/`로 이동하는 `real` 사용 7개 모듈, G3 학습 경로 전체, `mxu_bf16_128x128`.

## 9. 알려진 위험

- 64×64 상태를 1R1W SRAM으로 매 토큰 2회 읽기 + 1회 쓰기 → 뱅크 충돌. v1은 직렬로 피하고, v2에서 뱅크 분할.
- **현재 설계는 토큰당 상태를 3패스 한다** (`p=S·k` 읽기, `S←α·S+β·err·kᵀ` 읽기+쓰기, `o=S·q` 읽기).
  선행 연구 2603.05931 은 **상태 행렬당 읽기 1패스 + 쓰기 1패스**다 (5단계 파이프라인 데이터패스).
  **즉 DR1 v1 은 상태 트래픽에서 기준선보다 나쁘다.** 이것은 비트 정확 검증을 먼저 잡기 위해
  낸 대가이고, **융합은 W8 이후 과제**다 — 패스 융합은 중간 결과를 바꾸므로 골든도 같이 바뀐다.
  이 문장을 지우지 말 것 (`docs/PRIOR_ART.md` 1.1).
- Q1.15 상태는 장시간 누적 시 정밀도 손실. 골든 모델로 1,000토큰까지 비트 일치를 확인하고, 그 이상은 v2(BF16) 과제로 넘긴다.
- 델타룰 변형이 논문마다 다르다(정규화, 게이트 위치). v1은 2절 식 하나로 고정하고 다른 변형은 골든 모델 옵션으로만 둔다.
- `done_pulse` 계열 버그가 dr1_top FSM에서 재발할 수 있다. **G2 에서 이미 한 번 났다** (`docs/BUGS.md` BUG-001: fault 난 디스크립터가 완료 IRQ 를 올렸다). 그래서 5.1절에 완료 신호 계약(`done_ok`/`done_err`/`done_pulse`)을 정의했고, 7절 I6 으로 검사한다. 폭과 진입 경로를 파형(GTKWave)으로 직접 확인한다.
