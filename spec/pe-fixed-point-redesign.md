# PE 재설계 — PE 마다 FP32 가산기를 두지 않는다

## 왜 바꿨나

`mxu_bf16_16x16` 의 PE 는 매 사이클 완전한 FP32 덧셈을 했다. 정렬 시프트,
25단 정규화, 반올림이 전부 누산 루프 안에 있었다.

Yosys 로 PE 하나를 합성해 재 보면:

| | 셀 수 |
|---|---|
| PE 1개 | **4,369** |
| 16×16 타일 (PE 256개) | **1,118,464** |
| 128×128 PAR=8 (타일 64개) | **71,618,048** |

PAR=8 은 Verilator 가 C++ 를 784MB 넘게 뽑고도 끝나지 않았다. 합성은
애초에 불가능한 규모였다.

## 어떻게 바꿨나

곱을 고정소수점으로 정렬해 **더하기만** 한다. 정규화와 반올림은 누산
루프에서 빠져 출력으로 한 번만 간다.

```
이전:  BF16 곱 → FP32 정규화 → FP32 덧셈(정렬+정규화+반올림) → FP32 레지스터
이후:  BF16 곱 → 고정소수점 정렬(시프트) → 포화 덧셈 → 고정소수점 레지스터
                                                        └→ 출력에서 FP32 변환
```

매 사이클 임계 경로에 남는 것은 시프트와 덧셈뿐이다. 그리고 정수 영역에서
누산하므로 **K 에 대해 중간 반올림이 없다** — 이전보다 정확하다.

### 설계점

`rtl/bf16_pkg.sv`:

```systemverilog
localparam int ACC_W = 48;   // 누산기 폭 (2의 보수)
localparam int ACC_F = 16;   // 소수부 비트
```

| | 값 |
|---|---|
| 최대 크기 | 2^31 ≈ 2.1e9 |
| 분해능 | 2^-16 ≈ 1.5e-5 |
| 동적 범위 | 약 47 이진 자릿수 |

BF16 입력은 가수가 8비트뿐이라 이 분해능은 입력 정밀도를 넘는다.
범위를 벗어나면 **포화**시킨다 — 조용한 랩어라운드는 틀린 값을 그대로
흘려보내므로 쓰지 않았다.

BF16 지수 전 범위를 손실 없이 담으려면 약 520비트가 필요하다. PE 마다
둘 수 있는 크기가 아니다. 48비트는 신경망 GEMM 의 실제 값 분포를 기준으로
고른 설계점이고, 바꾸려면 `ACC_W`/`ACC_F` 두 상수만 손대면 된다.

## 측정 결과

```
pe_bench_fp32        셀 4,369   (타일 256개 기준 1,118,464)
pe_bench_fxp         셀 2,698   (타일 256개 기준   690,688)   1.62× 감소
pe_bench_fxp_loop    셀 1,978   (타일 256개 기준   506,368)   2.21× 감소
```

재현:

```bash
python3.13 sim/synth/area_pe.py pe_bench_fp32 pe_bench_fxp
python3.13 sim/synth/area_pe.py pe_bench_fxp_loop
```

`pe_bench_fxp_loop` 은 출력 변환을 뺀 누산 루프만이다. **매 사이클 임계
경로에 실제로 들어가는 부분이 2.21× 줄었다.**

### 최상위 1 탐색은 이진 탐색으로

`fxp_to_fp32` 의 최상위 비트 탐색을 48회 선형 루프로 쓰면 합성 시 48단
우선순위 체인이 되고, 시뮬레이터 엘라보레이션 비용도 PE 수에 비례해
폭증한다 (PAR=8 전체 회귀가 30분 한도에 걸렸다). 6단계 이진 탐색으로
바꿔 PE 2,811 → 2,698 셀이 되었고 PAR=8 빌드 시간도 크게 줄었다.

## 검증

`sim/cocotb/test_fxp_arith.py` — 산술 자체를 Python 부동소수점 기준값과
랜덤 차등 비교한다.

| 테스트 | 내용 |
|---|---|
| `test_mul_fxp_known` | 알려진 곱 8쌍 |
| `test_mul_fxp_random` | 랜덤 BF16 쌍 2,000개, 기준값과 완전 일치 |
| `test_add_sat` | 포화 덧셈 — 정상 구간 + 양/음 양쪽 넘침 |
| `test_to_fp32_known` | 알려진 변환 7개 |
| `test_to_fp32_random` | 랜덤 2,000개, **최대 상대오차 1.173e-07** |
| `test_end_to_end_dot` | K=64 내적 20회, 곱→누산→변환 전 과정 |

최대 상대오차 1.173e-07 은 FP32 가수 한계(2^-23 ≈ 1.19e-07) 바로 안쪽이다.
변환이 가능한 만큼 정확하다는 뜻이다.

기존 테스트벤치는 인터페이스가 그대로라 손대지 않았고 전부 통과한다.

## 남은 병목 — 솔직하게

출력 FP32 변환기가 PE 당 **720 셀**(2,698 − 1,978), PE 비용의 27% 다.
`acc_out` 이 16×16 FP32 배열을 조합으로 전부 내보내는 인터페이스라
변환기가 PE 마다 하나씩 필요하다.

읽기는 GEMM 타일당 한 번뿐이므로, **변환기 1개를 타일이 공유하고 순차로
읽어내면** 타일당 184,320 셀이 빠진다. 다만 인터페이스가 스트리밍
읽기로 바뀌어 `mxu_bf16_128x128` 과 테스트벤치가 전부 영향을 받는다.
이번에는 인터페이스를 건드리지 않는 쪽을 택했다.

### 그리고 PAR=8 은 여전히 FPGA 에 안 들어간다

재설계 후에도:

| 구성 | MAC | 셀 (근사) |
|---|---|---|
| PAR=1 | 256 | 690,688 |
| PAR=2 | 1,024 | 2,762,752 |
| PAR=4 | 4,096 | 11,051,008 |
| PAR=8 | 16,384 | 44,204,032 |

1.62× 로는 7,160만을 FPGA 에 넣을 수 없다. **MAC 배열 자체가 큰 것이고
그건 줄일 수 없다** — 16,384 MAC 은 원래 데이터센터급 블록이다
(TPU v1 의 시스톨릭 배열이 256×256 = 65,536 MAC 이었다).

현실적인 FPGA 설계점은 **PAR=4** 다. 재설계의 값어치는 PAR=8 을 가능하게
만든 데 있지 않고, 임계 경로를 2.21× 줄이고 누산 정확도를 올린 데 있다.

# 후속: 공유 변환기 + 순차 읽기

위에서 "남은 병목" 으로 남겨둔 출력 변환기를 파라미터로 분리했다.

## 인터페이스

`mxu_bf16_16x16` 과 `mxu_bf16_128x128` 에 같은 파라미터 두 개가 생겼다.

| 파라미터 | 기본 | 뜻 |
|---|---|---|
| `FP32_OUT` | 1 | `acc_out`/`acc_flat` 에 FP32 배열을 조합으로 내보낸다. PE 마다 변환기가 붙는다. |
| `STREAM_RD` | 0 | `rd_idx`/`rd_fp32` 로 순차 읽기. 변환기 하나를 타일이 공유한다. |

**기본값은 이전과 완전히 동일하다.** 기존 테스트벤치는 한 줄도 바뀌지 않았다.

`STREAM_RD=1` 은 `PAR == TILES` 일 때만 쓸 수 있다. `PAR` 이 작으면
누산값이 타일이 아니라 외부 `acc_mem` 에 있어서 타일을 읽어봐야 의미가
없다. 파라미터 검사에서 `$fatal` 로 막는다.

## 측정

```
conv_bench   셀    830   변환기 1개
rd_bench     셀 40,926   256:1 먹스 트리 + 변환기 1개
```

타일(256 PE) 기준 합산:

| 구성 | 계산 | 셀 |
|---|---|---|
| PE 마다 변환기 | 256 × 2,698 | 690,688 |
| 타일당 변환기 1개 | 256 × 1,978 + 40,926 | **547,294** |

**143,394 셀 절감 (20.8%).**

앞서 문서에 적었던 184,320 은 틀린 추정이었다. 변환기 255개가 빠지는
대신 **256:1 먹스 트리가 40,096 셀** 들어온다. 그 비용을 빼면 14.3만이다.

PAR=8 전체로는 64 타일 × 547,294 = **35,026,816 셀** (이전 44,204,032).
여전히 FPGA 에는 들어가지 않는다. 결론은 바뀌지 않는다 — MAC 배열
자체가 큰 것이고, 현실적인 FPGA 설계점은 PAR=4 다.

## 검증

`sim/cocotb/test_mxu128_stream_rd.py` (PAR=8, FP32_OUT=0, STREAM_RD=1):

- 타일 경계를 넘는 6개 위치에서 K=3 누산값을 순차 읽기로 확인
- 위치마다 서로 다른 값이 나오는지 — 읽기 라우팅이 실제로 동작하는 확인
- `acc_flat` 이 전부 0 인지 — PE 변환기가 실제로 제거됐다는 구조적 확인

`sim/cocotb/run_all.py` 의 `VARIANTS` 표에 등록돼 일반 회귀에 함께 돈다.
