# gemm_core 메모리 분석 — MAC 배열이 6~25% 만 일한다

## 측정

`sim/cocotb/test_gemm_utilization.py` 가 FSM 상태별 사이클을 센다.

```bash
PATH=/opt/verilator/bin:$PATH python3.13 sim/cocotb/run_util.py
```

| Kt | 전체 | 연산 | 페치 | 쓰기 | 가동률 |
|---:|---:|---:|---:|---:|---:|
| 1 | 79 | 5 | 4 | 65 | **6.3%** |
| 4 | 88 | 8 | 10 | 65 | **9.1%** |
| 16 | 124 | 20 | 34 | 65 | **16.1%** |
| 64 | 268 | 68 | 130 | 65 | **25.4%** |

FSM 이 `ACT 읽기 → WGT 읽기 → 연산 → 쓰기` 로 완전히 직렬이라
페치 동안 MAC 배열이 통째로 놀고, 연산 동안 DMA 가 논다.

쓰기가 Kt 와 무관하게 **고정 65 사이클**인 것도 눈에 띈다.
16×16 INT32 결과 = 1,024 바이트, 16 바이트/비트 DMA 로 64 비트 + 요청 1.

## 그런데 겹치기만으로는 안 된다

`gemm_core` 는 읽기(`rd_*`)와 쓰기(`wr_*`)가 **독립 채널**이다. 둘은
서로 겹칠 수 있으므로 각각 따로 세어야 한다.

Kt=64 한 번에 필요한 **채널별 비트 수**:

| 채널 | 비트 | 바이트 |
|---|---:|---:|
| 읽기 (ACT 64 + WGT 64) | **128** | 2,048 |
| 쓰기 (결과) | 64 | 1,024 |
| 연산 | — | (68 사이클) |

읽기 채널이 묶이는 쪽이다.

```
연산 68  :  읽기 128   →  읽기 대역폭이 1.9 배 모자라다
```

**완벽하게 겹쳐도 가동률 상한은 68/128 = 53% 다.** 지금 25.4% 이므로
겹치기로 약 2배를 얻고 거기서 멈춘다.

### 산술 강도

GEMM 타일 하나(16×16, K=64):

```
연산량      2 × 16 × 16 × 64 = 32,768 FLOP
읽기 바이트 2,048
강도        16 FLOP/byte  (읽기 기준)
```

128비트 @1GHz = 16 GB/s 읽기 포트로는 256 GFLOP/s 가 상한이다.
MXU 가 PAR=4 (4,096 MAC, 8.2 TFLOP/s @1GHz)라면 **32배 모자라다.**

## 그래서 고칠 것은 두 가지다

1. **겹치기** — 이중 버퍼링으로 페치/연산/쓰기를 중첩한다.
   25.4% → 53%. 상한까지 끌어올리지만 거기까지다.
2. **대역폭** — 읽기 데이터 폭을 넓힌다. 이게 본질이다.

| 읽기 폭 | 읽기 사이클 (Kt=64) | 가동률 상한 |
|---:|---:|---:|
| 128비트 (현재) | 128 | 53% |
| 256비트 | 64 | 100% (연산 한계) |

**256비트 읽기 포트면 PAR=1 MXU 하나가 연산 한계에 닿는다.** PAR=4 면
그 4배, PAR=8 이면 8배가 필요하다.

이것이 H200 이 4.8 TB/s HBM3e 를 쓰는 이유다. 연산을 아무리 키워도
먹일 수 없으면 의미가 없다. 앞선 문서
(`spec/pe-fixed-point-redesign.md`)에서 연산은 H200 의 17배 안쪽까지
좁혔지만, 메모리는 그보다 훨씬 먼 거리에 있다.

## 측정 방법에 대한 주의

`test_gemm_utilization.py` 는 **실패시키지 않는다.** 개선 전후를 같은
자로 재기 위한 기준선이고, 숫자를 로그에 남긴다. 회귀에서 깨지면
안 되는 것은 FSM 이 실제로 동작한다는 사실뿐이라 그것만 단언한다.

DMA 스텁(`sim/cocotb/dma_stub.py`)은 지연 없이 즉시 응답한다. 실제
메모리는 더 느리므로 **위 숫자는 낙관적인 상한이다.**

# 1단계 적용: 쓰기 FSM 분리

## 바꾼 것

쓰기(`S_WR_REQ`/`S_WR_SEND`/`S_DONE`)를 메인 FSM 에서 떼어내
독립 FSM `wst` 로 옮겼다. 메인 FSM 은 `S_LATCH` 에서 결과를
`acc_out_lat` 에 옮기고 **곧바로 `S_IDLE` 로 돌아가** 다음 디스크립터를
받는다. 쓰기는 그 뒤에서 혼자 드레인한다.

읽기(`rd_*`)와 쓰기(`wr_*`)가 독립 채널이라 가능한 일이다.

### 해저드 하나

`acc_out_lat` 은 단일 버퍼다. 두 가지로 막았다.

1. 메인 FSM 은 `S_LATCH` 에서 `wst == W_IDLE` 을 기다린다.
2. `acc_out_lat` 을 `S_ACC_CLR` 에서 지우던 코드를 래치 시점으로 접었다.
   그대로 두면 다음 디스크립터가 `S_ACC_CLR` 에 닿을 때 아직 전송 중인
   버퍼를 지운다. `Kt=0` 이면 0 을 래치하므로 동작은 같다.

## 측정

단일 디스크립터로는 겹칠 상대가 없어 이득이 0이다. 처리량으로 재야 한다.
`sim/cocotb/test_gemm_core_throughput.py` 가 `gemm_core` 에 직접 명령을
연속으로 밀어 넣는다.

| Kt | 단일 (이전) | 연속 op당 (이후) | |
|---:|---:|---:|---|
| 1 | 79 | **68.4** | 쓰기 65 사이클이 병목 — 완전히 겹쳤다 |
| 16 | 124 | **74.0** | 1.68× |
| 64 | 268 | **210.1** | 1.28× |

Kt=1 에서 68.4 는 쓰기 채널(65 비트)이 포화됐다는 뜻이다. 더 줄일 수
있는 여지가 그쪽엔 없다.

Kt=64 의 210 은 `페치 130 + 연산 68 + 오버헤드` 다. 쓰기는 그 밑에
완전히 숨었다. **이제 임계 경로는 페치→연산 직렬이다.**

## 2단계 적용: ctrl_fsm 파이프라인

처음에는 위 이득이 `gemm_top` 경유로는 전혀 보이지 않았다.
`ctrl_fsm` 이 `ST_DISPATCH` 다음에 `ST_WAIT` 로 가서 `core_done` 을
기다린 뒤에야 `ST_IDLE` 로 돌아가 `desc_ready` 를 올렸기 때문이다.

발행 경로와 완료 경로를 분리했다.

```
발행:  ST_IDLE → ST_LATCH → ST_DECODE → ST_DISPATCH → ST_IDLE
완료:  core_done 을 그대로 흘려보낸다
       (GEMM 이 아닌 디스크립터는 ST_DONE 에서 자체 생성)
```

`gemm_top` 의 커맨드 브리지가 `cmd_valid` 를 코어 수용 시점까지 유지하고
그때 `cmd_ready_ctrl` 을 올리므로, `ST_DISPATCH` 를 빠져나오는 순간
래치/디코드 레지스터를 덮어써도 안전하다.

`core_done` 과 비 GEMM 디스크립터의 `ST_DONE` 이 같은 사이클에 겹칠 수
있어서 완료 펄스를 큐에 쌓아 한 사이클짜리로 하나씩 낸다. `busy` 는
코어에 떠 있는 명령 수(`outstanding`)와 큐를 함께 본다.

### gemm_top 경유 처리량 (op 당 사이클)

| Kt | 이전 | 이후 | 코어 직접 |
|---:|---:|---:|---:|
| 1 | 85.8 | **71.2** | 68.4 |
| 16 | 130.8 | **82.5** | 74.0 |
| 64 | 274.8 | **219.8** | 210.1 |

시스템 처리량이 코어 자체 처리량에 거의 붙었다. 남은 ~10 사이클은
디스크립터 래치/디코드 오버헤드다.

## 남은 단계

| 단계 | Kt=64 op당 (코어) | 가동률 |
|---|---:|---:|
| 원본 (완전 직렬) | 268 | 25.4% |
| **쓰기 FSM 분리 (적용됨)** | **210** | **32.4%** |
| **ctrl_fsm 파이프라인 (적용됨)** | 시스템 274.8 → **219.8** | — |
| 피연산자 이중 버퍼링 | ~130 | ~52% |
| 읽기 폭 256비트 | ~68 | ~100% (연산 한계) |

피연산자 이중 버퍼링은 `act_sram`/`wgt_sram` 에 뱅크 비트를 더하고
페치 FSM 을 연산 FSM 에서 분리하는 작업이다. 그러면 페치(130)가
연산(68)+쓰기(65) 와 겹쳐 주기가 `max(130, 133)` 로 떨어진다.
거기서부터는 읽기 대역폭이 벽이고, 그 벽은 FSM 으로 넘을 수 없다.

## 테스트벤치 샘플링 주의

`await RisingEdge(clk)` 직후에 읽으면 **엣지가 반영되기 전** 값이 보인다.
핸드셰이크를 그렇게 세면 같은 명령을 두 번 수용한 것으로 집계된다
(실제로 이 테스트를 쓰다가 그 버그를 냈다). `Timer(1ns)` 로 한 델타
넘긴 뒤에 읽어야 한다. `tb_oom_guard_*` 의 `settle()` 과 같은 문제다.

# 3단계: 읽기 폭 파라미터화 — 그리고 그 과정에서 찾은 버그

## 먼저, gemm_core 는 Kt>1 에서 틀린 값을 냈다

읽기 폭을 넓히고 결과를 numpy 기준값과 대조하는 테스트를 쓰다가
**폭과 무관한 기존 버그**를 발견했다. 128비트 그대로도 Kt=2 부터 틀린다.

```
assign mac_en = mac_en_d2;        // 발행 3사이클 뒤
```

피연산자는 발행 **1사이클** 뒤에 SRAM 출력에 나온다. SRAM 출력은 다음
읽기 전까지 유지되므로, 연속 발행하면 피연산자가 t+1 부터 매 사이클
넘어가는데 MAC 은 t+3 부터 먹기 시작한다. 앞쪽 K-step 을 놓치고
마지막 것을 중복 누적한다.

파형으로 잡은 Kt=2 의 모습:

```
[ 8] COMPUTE  re=1 kmux=0  mac_en=0  rdata=00000000
[ 9] COMPUTE  re=1 kmux=1  mac_en=0  rdata=03020100   ← K-step 0, 그런데 MAC off
[10] COMPUTE  re=0 kmux=1  mac_en=0  rdata=13121110   ← K-step 1
[11] COMPUTE  re=0 kmux=1  mac_en=1  rdata=13121110   ← K-step 1 을 먹는다
[12] COMPUTE  re=0 kmux=1  mac_en=1  rdata=13121110   ← 또 K-step 1
```

K-step 1 을 두 번 누적하고 K-step 0 은 버렸다.

**Kt=1 에서는 피연산자가 하나뿐이라 우연히 맞는다.** 그리고
`sim/cocotb/test_gemm_top.py` 는 주석에 "🔥 문제 고정: Kt=1만" 이라고
적고 Kt=1 만 돌린다. 그래서 드러난 적이 없었다.

수정:

```systemverilog
assign mac_en = act_issue_d & wgt_issue_d;   // 발행 1사이클 뒤
```

`issue_k_mac` 카운터도 같은 신호를 세도록 맞췄다.

> 이 저장소에서 찾은 **세 번째** K>1 누적 버그다.
> 앞의 둘은 `mxu_bf16_128x128` 의 정수 덧셈 누적
> (`spec/mxu-128x128-rewrite.md`) 과 `trace_ring` 의 head 전진
> (`spec/verification-infrastructure.md`). 공통점은 전부
> **K=1 또는 랩어라운드 전까지만 테스트돼 있었다**는 것이다.

## 읽기 폭 파라미터

`gemm_core` 와 `gemm_top` 에 `RD_DATA_W` (128 또는 256, 기본 128).

한 K-step 은 INT8 16개 = 128비트다. 256 이면 비트 하나가 K-step 두 개를
나른다. 전송 바이트 수는 같고 **비트 수가 절반**이 된다.

- `act_sram`/`wgt_sram` 은 `DATA_W`/`DEPTH` 파라미터를 받는다.
  워드 폭 = 읽기 폭, 워드 수 = `MAX_KT / KPW`.
- 연산 쪽은 K 인덱스를 (워드 주소, 워드 내 위치) 로 나눠 절반을 고른다.
  SRAM 이 동기 읽기이고 `re=0` 일 때 출력을 유지하므로, 위치 선택
  레지스터도 `act_re` 일 때만 갱신해 같은 성질을 맞춘다.
- 요청 길이는 비트 크기로 올림한다. Kt 가 홀수면 `Kt*16` 바이트가
  32 의 배수가 아니다. 남는 절반은 쓰이지 않는다.
- **쓰기 채널은 건드리지 않았다.** 독립 채널이고 병목이 아니다.

## 측정 — 코어 연속 처리량 (op 당 사이클)

| Kt | 128비트 | 256비트 | |
|---:|---:|---:|---|
| 1 | 68.1 (4.4%) | 68.1 (4.4%) | 쓰기 채널 포화 — 읽기와 무관 |
| 16 | 73.8 (24.4%) | 71.8 (25.1%) | |
| 64 | 208.1 (31.7%) | **144.1 (45.8%)** | **1.44×** |

단일 디스크립터 지연도 Kt=64 에서 270 → 206 사이클로 줄었고,
읽기 비트는 128 → 64 로 정확히 절반이 됐다.

## 전체 경과

| 단계 | Kt=64 op당 | 가동률 |
|---|---:|---:|
| 원본 (완전 직렬, 게다가 결과도 틀림) | 268 | 25.4% |
| 쓰기 FSM 분리 | 210 | 32.4% |
| ctrl_fsm 파이프라인 | 시스템 274.8 → 219.8 | — |
| mac_en 정렬 (정확성 수정) | 208.1 | 31.7% |
| **읽기 폭 256비트** | **144.1** | **45.8%** |
| 피연산자 이중 버퍼링 (남음) | ~70 | ~100% |

256비트에서 읽기 64 비트, 쓰기 64 비트, 연산 68 사이클이 되어 **이제
연산이 묶는 쪽이다.** 남은 144 − 68 = 76 사이클은 디스크립터 안에서
페치와 연산이 아직 직렬이기 때문이고, 그것이 피연산자 이중 버퍼링으로
없앨 수 있는 마지막 덩어리다.

# 4단계: 피연산자 이중 버퍼링 — 그리고 앞서 쓴 숫자의 정정

## 먼저 정정

3단계까지 이 문서에 적은 "op당 사이클" 은 디스크립터 **8개** 를 흘려보낸
전체 사이클을 8로 나눈 값이다. 설계가 직렬일 때는 채움/배출이 없으니
그게 곧 주기였지만, 파이프라인이 되고 나면 8개로는 꼬리가 амortize 되지
않아 주기를 과대평가한다. 아래부터는 **완료 펄스 사이 간격** 을 직접
재고, 앞뒤 2개를 버린 정상상태 값을 쓴다. 비교용으로 8-op 평균도 같이
남긴다.

## 설계

로드 / 연산 / 쓰기를 세 FSM 으로 완전히 분리했다. 서로 다른 자원을
쓰므로 서로 다른 디스크립터를 동시에 처리할 수 있다.

```
  로드 FSM (lst)  DMA 읽기 채널, SRAM 쓰기 포트
  연산 FSM (cst)  SRAM 읽기 포트, MAC 배열, 누산기
  쓰기 FSM (wst)  DMA 쓰기 채널
```

묶이는 지점은 둘뿐이다.

1. **피연산자 SRAM — 뱅크 이중 버퍼.** 로드가 뱅크 B 를 채우는 동안
   연산이 뱅크 A 를 읽는다. `bank_full` 비트로 주고받고, 주소 상위에
   뱅크 인덱스를 붙여 구현한다. 256비트에서 뱅크 깊이가 절반이 되므로
   **총 SRAM 비트 수는 원래의 단일 버퍼 128비트 구성과 같다.**
2. **`acc_out_lat` — 단일 버퍼.** 연산 FSM 은 `C_LATCH` 에서 쓰기 FSM 이
   비기를 기다린다.

`bank_full` 의 set(로드) 과 clear(연산) 가 같은 사이클에 일어날 수 있지만
같은 뱅크에는 겹치지 않는다. set 은 `bank_full=0` 인 뱅크에서만
(`cmd_ready` 조건), clear 는 `bank_full=1` 인 뱅크에서만 일어나므로 두
뱅크는 항상 다르다. 이 논증이 틀리면 두 대입이 조용히 충돌하므로,
`COCOTB_SIM` 아래에 `$fatal` 검사를 넣어 터뜨리게 했다.

## 정상상태 측정 (Kt=64)

`sim/cocotb/test_pipe_profile.py` 가 세 FSM 의 상태 점유와 완료 간격을
같이 잰다. 24개를 흘려보낸 결과, 간격이 전 구간에서 **한 사이클도
흔들리지 않았다** (131 × 23, 70 × 23).

| | 128비트 | 256비트 |
|---|---:|---:|
| 정상상태 간격 | **131.0** 사이클/op | **70.0** 사이클/op |
| 가동률 | 48.9% | **91.4%** |
| 로드 FSM 바쁨 | **95.2%** | 87.4% |
| 연산 FSM 바쁨 | 50.5% | **91.4%** |
| 쓰기 FSM 바쁨 | 48.3% | 87.4% |

**128비트는 로드가 묶는 쪽이다.** 로드 경로가
`1 + Kt + 1 + Kt = 130` 사이클을 쓰는데 측정 간격이 131 이고 로드 FSM 이
95.2% 바쁘다. 읽기 채널이 바닥이라 더 짤 데가 없다.

**256비트는 연산이 묶는 쪽이다.** 로드가 `1 + 32 + 1 + 32 = 66`,
쓰기가 `1 + 64 + 1 = 66`, 연산이
`C_CLR 1 + C_COMPUTE 66 + C_POST 1 + C_LATCH 1 = 69` 이고 측정 간격이
70 이다. MAC 배열이 64 사이클 중 64 를 일하고 나머지 6 이 상태 전이다.
여기서 더 가려면 DMA 가 아니라 MAC 배열을 늘려야 한다.

## 틀렸던 가설 하나

처음에는 8-op 평균 86.5 를 보고 "뱅크가 2개뿐이라 로드와 연산이 서로를
기다린다" 고 생각해 `BANKS` 를 파라미터로 빼고 4로 올려 재봤다.
**전체 사이클이 1 도 바뀌지 않았다** (692 → 692, 세 FSM 점유도 동일).
거품은 뱅크 깊이가 아니라 8개 구간의 파이프라인 채움/배출이었고,
24개로 늘려 정상상태를 직접 재니 70.0 이 나왔다.

`BANKS` 파라미터는 남겼다 (기본 2). 쓸모가 증명되지 않았다는 점을
여기 적어 둔다 — 2보다 키울 이유는 현재 측정에 없다.

## 전 경과 (Kt=64)

| 단계 | 8-op 평균 | 정상상태 | 가동률 |
|---|---:|---:|---:|
| 원본 (완전 직렬, 게다가 결과도 틀림) | 268 | — | 25.4% |
| 쓰기 FSM 분리 | 210 | — | 32.4% |
| ctrl_fsm 파이프라인 | — | — | — |
| mac_en 정렬 (정확성 수정) | 208.1 | — | 31.7% |
| 읽기 폭 256비트 | 144.1 | — | 45.8% |
| **피연산자 이중 버퍼링, 128비트** | 147.9 | **131.0** | **48.9%** |
| **피연산자 이중 버퍼링, 256비트** | 86.5 | **70.0** | **91.4%** |

256비트 구성에서 원본 268 대비 정상상태 **3.8배**, 가동률 25.4% →
91.4% 다. 남은 8.6% 는 디스크립터당 상태 전이 6 사이클이고, 그것을
없애려면 MAC 배열을 멈추지 않고 다음 K-루프를 시작할 수 있게
누산기를 이중화해야 한다 — 256 × 32비트 × 2 = 16Kb 의 플립플롭이다.
1.09배를 위한 값으로는 비싸므로 하지 않았다.

# 5단계: Weight-stationary — 대역폭 벽을 설계로 피하기

## 왜 이것이 본질인가

4단계까지는 칩 *안쪽* 을 고쳤다. 가동률 25.4% → 91.4%. 하지만 칩 *바깥*
으로 나가는 트래픽 자체는 한 번도 줄이지 않았다. 디스크립터마다 ACT 와
WGT 를 둘 다 읽었고, 그 절반은 **같은 가중치를 다시 읽는 것**이었다.

LLM 추론에서 한 레이어의 가중치는 그 레이어를 지나는 모든 활성값 타일에
대해 같다. 한 번 읽으면 된다.

### 사례와 선행 연구

| 설계 | 접근 | 대역폭 |
|---|---|---|
| H200 | HBM3e | 4.8 TB/s |
| Groq LPU (1세대) | 230 MB SRAM, DRAM 을 임계 경로에서 제거 | 80 TB/s (벤더 주장) |
| Cerebras WSE-3 | 44 GB 온웨이퍼 SRAM | 21 PB/s (벤더 주장) |

둘 다 **DRAM 대역폭을 늘려서 이긴 게 아니라, DRAM 을 안 쓰는 쪽으로
설계를 바꿔서** 이겼다. 용량이 대가다 (Groq 는 칩당 230 MB).

Eyeriss (Chen/Emer/Sze, ISCA 2016) 의 데이터플로 분류가 같은 원리를
일반화한다: weight-stationary / output-stationary / input-stationary /
row-stationary. 그 논문은 데이터플로만 바꿔 AlexNet DRAM 접근을
**2,896M → 61M (47×)** 로 줄였다.

> 벤더 수치는 독립 벤치마크로 확인하지 못했다. Groq 의 80 TB/s 는 자사
> 백서 수치이고, 비교 대상 GPU 세대에 따라 배수가 7×~10× 로 달라진다.

## 구현

디스크립터 바이트 1 (flags) bit0 = `FLAG_WGT_KEEP`. 서면 로드 FSM 이
WGT 단계를 건너뛰고 SRAM 에 상주한 가중치를 쓴다.

가중치 SRAM 도 2 뱅크지만 **포인터가 실제 적재 때만 전진한다.**
건너뛴 디스크립터는 직전에 적재된 뱅크(`wres_bank`)를 가리킨다.

**안전성 증명.** 활성값 뱅크가 2개이므로 로드 FSM 은 연산 FSM 보다 최대
한 디스크립터 앞선다. 디스크립터 N 을 연산하는 동안 로드가 N+1 을
적재한다고 하자.
- N 이 적재했다면 `wgt_bank_of[N]=w` 이고, 그 적재가 끝나며 `wld=~w` 다.
- N 이 건너뛰었다면 `wgt_bank_of[N]=wres=w` 이고 `wld` 는 그대로 `~w` 다.

두 경우 모두 N+1 이 적재할 뱅크(`~w`)가 N 이 읽는 뱅크(`w`)와 다르다. ∎

그래서 **드레인이 필요 없다** — `wgt_keep=0` 경로도 완전히 파이프라인된
채로 남는다 (기존 테스트 전부가 그 경로다).

### 구현 중 잡은 버그

처음엔 `wld_bank` 를 `cmd_accept` 에서 전진시켰다. 적재는 그 뒤에
일어나므로 로드 FSM 이 **다음** 뱅크에 써 버렸고, 결과가 전부 0 이
나왔다 (`wgt_keep=0` 인 기존 경로까지 깨졌다). 포인터 전진을 수신
마지막 비트(`wgt_load_done`)로 옮겨 고쳤다.

## 측정 1 — 트래픽

가중치 하나에 활성값 4개를 통과시킨 결과 (Kt=16, 128비트):

```
읽기 비트: [32, 16, 16, 16]     ← 첫 번째만 가중치 적재
총 80 비트 vs 매번 재적재 128 비트 → 1.60× 절감
```

재사용 디스크립터가 정확히 절반(16 vs 32)이다. N 개가 재사용하면
절감은 `2N/(N+1)` 이고, N→∞ 에서 **2×** 다.

## 측정 2 — 처리량 (정상상태, Kt=64, 24개 연속)

| 읽기 폭 | WS | 간격/op | 가동률 | 로드 FSM 바쁨 |
|---|---|---:|---:|---:|
| 128비트 | off | 131.0 | 48.9% | **95.2%** |
| 128비트 | **ON** | **70.0** | **91.4%** | 86.6% |
| 256비트 | off | 70.0 | 91.4% | 87.4% |
| 256비트 | **ON** | **70.0** | **91.4%** | **45.5%** |

두 가지가 드러난다.

1. **128비트에서도 연산 한계에 닿는다.** 131 → 70, 가동률 48.9% →
   91.4%. 3단계에서 버스를 256비트로 넓혀 얻은 것과 **같은 결과를
   버스를 넓히지 않고** 얻는다. 데이터플로가 배선보다 싸다.
2. **256비트 + WS 에서 로드 채널이 45.5% 만 바쁘다.** 읽기 채널에
   **2.2× 여유**가 생겼다. 이것이 다음 단계의 재료다 — 지금은 연산이
   묶는 쪽이고, 그 연산을 키울 대역폭이 남아 있다.

## 산술 강도로 확인

256비트 = 사이클당 32바이트. WS 면 디스크립터당 활성값 `Kt×16` 바이트로
`Kt×256` MAC 을 한다 → **16 MAC/바이트 = 32 OPS/바이트.**

```
먹일 수 있는 양   32 B/cycle × 32 OPS/B = 1,024 OPS/cycle
실제 쓰는 양      256 MAC × 2 × 0.914   =   468 OPS/cycle
여유                                        2.19×
```

측정된 로드 유휴 54.5% 와 맞는다 (1/2.19 = 45.7% ≈ 45.5%).

**결론: 이제 MAC 배열을 키울 차례다.** 대역폭이 아니라 연산이 부족하다.

# 6단계: 타일 확장 — 남은 대역폭 여유를 연산으로 바꾸기

5단계 끝에서 측정이 분명히 말했다: 256비트 + weight-stationary 에서 로드
채널이 45.5% 만 바쁘다. 대역폭이 아니라 **연산이 부족하다.**

## 왜 타일을 키우는 것이 정답인가

N×N 외적 누산에서 MAC 은 N², 피연산자 바이트는 N 이다. 즉

```
산술 강도 = N² MAC / N 바이트 = N MAC/바이트
```

**산술 강도가 N 에 비례한다.** 타일을 2배로 키우면 연산은 4배, 피연산자는
2배다. 이것이 대역폭 대비 연산을 늘리는 정석 경로이고, 더 많은 작은
타일을 병렬로 놓는 것과 질적으로 다르다 (타일을 늘리면 피연산자도 선형으로
늘어 강도가 그대로다).

| N | MAC | K-step 바이트 | 강도 (MAC/B) |
|---:|---:|---:|---:|
| 16 | 256 | 16 | 16 |
| 32 | 1,024 | 32 | **32** |

## 함께 필요한 것: 쓰기 폭

디스크립터당 출력은 N² 인데 연산은 Kt 사이클이다. N=16/Kt=64 에서는
쓰기 64 비트 vs 연산 64 사이클로 균형이지만, N=32 는 출력이 1,024개
(4,096바이트) 라 128비트 쓰기로는 **쓰기가 묶는 쪽**이 된다.
`WR_DATA_W` 를 파라미터로 빼서 256비트로 맞췄다.

균형점은 `Kt = N²·4 / (WR_DATA_W/8)`. N=32 / 256비트 쓰기면 Kt=128 이다.

## 측정 (정상상태, 24개 연속, weight-stationary ON)

| TILE_N | RD/WR | Kt | 간격/op | MAC/사이클 | INT8 OPS/사이클 | 가동률 |
|---:|---|---:|---:|---:|---:|---:|
| 16 | 128/128 | 64 | 70 | 234 | 468 | 91.4% |
| 16 | 256/256 | 32 | 38 | 216 | 431 | 84.2% |
| **32** | **256/256** | **128** | **134** | **978** | **1,956** | **95.5%** |

**N=32 가 N=16 대비 4.18×.** 가동률도 91.4% → 95.5% 로 올랐다 — Kt=128 이
디스크립터당 고정 오버헤드(상태 전이 6 사이클)를 더 잘 분산시킨다.

N=16/256비트의 84.2% 는 반대 방향을 보여준다. Kt=32 로 짧아져 오버헤드
비중이 커졌다. 타일이 작으면 넓은 버스가 오히려 낭비다.

## 면적

`mac_pe` 를 Yosys 로 실측한 뒤 환산했다. Yosys 0.33 은 unpacked array
포트를 파싱하지 못해 배열 전체를 합성할 수 없다 (이 저장소가 PE 단위로
재는 이유이고, `spec/pe-fixed-point-redesign.md` 에 같은 제약이 적혀 있다).

```
mac_pe   셀 817,  논리 단수 67 (2입력 게이트 기준)   ← 실측
N=16     256 × 817 =   209,152 셀
N=32   1,024 × 817 =   836,608 셀
```

4배 면적으로 4.18배 처리량이다. 효율이 1 을 넘는 것은 가동률이 같이
오른 덕이다.

> 논리 단수 67 은 `mac_pe` 가 8×8 곱셈과 32비트 누산을 **한 사이클
> 조합논리로** 하기 때문이다. 이것이 임계 경로이고 클럭을 묶는다.
> 실제 Vivado 는 이 곱셈·누산을 DSP58 하드 블록으로 뽑을 것이므로 위
> 셀 수는 FPGA 실물과 다르다. 배치·배선을 돌리지 않았으므로
> **동작 주파수는 이 저장소에서 측정된 값이 없다.**

## 파라미터 제약 (RTL 에서 `$fatal` 로 강제)

```
KPW = RD_DATA_W / (TILE_N*8)        정수이고 >= 1
N² 가 WR_DATA_W/32 의 배수
WR_DATA_W, RD_DATA_W ∈ {128, 256}
BANKS 는 2의 거듭제곱 >= 2
```

N=32 는 K-step 이 32바이트이므로 `RD_DATA_W >= 256` 을 요구한다.
구성이 어긋나면 합성 전에 터진다.

## 그 과정에서 찾은 버그 — 디스크립터 핸드셰이크

32×32 를 연속으로 흘려보내는 테스트를 쓰자 **첫 디스크립터의 결과가 전부
0** 으로 나왔다. 타일과 무관한 기존 버그였다.

`ctrl_fsm` 은 `desc_ready` 를 `ST_IDLE` 에서 세우고 `desc_bytes` 를
`ST_LATCH` (한 사이클 뒤)에 읽었다.

```
사이클 t    ST_IDLE   desc_ready=1, desc_valid=1  → 핸드셰이크 성립
사이클 t+1  ST_LATCH  latched <= desc_bytes       ← 여기서 읽는다
```

AXI-Stream 규약은 `valid && ready` 가 성립한 사이클에 데이터가 소비되고
그 다음부터 생산자가 바꿀 수 있다고 한다. 즉 이 FSM 은 호스트에게
**핸드셰이크 이후에도 한 사이클 더 들고 있으라고** 요구했다. 규약을
지키는 호스트가 바로 다음 디스크립터를 올리면 이전 것 자리에 **다음**
것의 바이트가 들어간다 — 결과가 한 칸씩 밀리고 첫 주소가 빈다.

디스크립터를 하나씩만 보내면 드러나지 않는다. `test_gemm_utilization` 의
스트림 테스트는 같은 구조로 밀어 넣었지만 완료 **개수**만 단언하고
결과를 대조하지 않아서 지나쳤다.

`g3_desc_fsm` 에 같은 패턴이 있어 같이 고쳤다. 수정은 핸드셰이크 사이클에
캡처하는 것뿐이다.

```systemverilog
wire desc_accept = desc_valid & desc_ready;
always_ff @(posedge clk)
  if (desc_accept) ... latched[i] <= desc_bytes[i];
```

`sim/cocotb/test_desc_handshake.py` 가 규약을 강제한다 — 핸드셰이크 직후
`desc_bytes` 를 `0xFF` 로 덮고도 결과가 맞아야 한다.

> 이 저장소에서 찾은 **네 번째** 조용한 버그다. 앞의 셋은 모두 K>1 누산
> (`mxu_bf16_128x128` 정수 덧셈, `trace_ring` head 전진, `gemm_core`
> mac_en 정렬). 이번 것은 호스트 인터페이스이고, 공통점은 같다 —
> **단일 트랜잭션만 테스트돼 있었다.**

## 테스트를 자기설정형으로

처음엔 `TILE_N` 을 환경변수로만 받았는데 러너가 그 값을 Verilator 에
넘기지 않았다. RTL 은 N=16, 테스트는 N=32 를 가정해 1,008/1,024 개가
조용히 틀렸다.

이제 테스트가 구성을 **DUT 에서 직접 읽는다.**

```python
accs    = len(dut.u_core.acc_out_lat)   # N²
n       = int(round(accs ** 0.5))
rd_beat = len(dut.rd_data) // 8
wr_beat = len(dut.wr_data) // 8
```

환경변수와 RTL 이 어긋나는 것이 원천적으로 불가능해진다.

# 7단계: INT4 가중치 — 메모리에 묶인 경로를 두 배로

## 왜 이것이 LLM 추론에 결정적인가

단일 스트림 디코드는 **토큰마다 가중치 전체를 한 번 읽는 데** 묶인다.
연산이 아니라 그 바이트가 토큰 속도를 정한다.

```
토큰 속도 = 메모리 대역폭 / 가중치 바이트
```

가중치를 INT4 로 두면 분모가 절반이 되고 토큰 속도가 **그대로 두 배**다.
weight-stationary 는 배치가 있어야 효과가 나지만, INT4 는 **배치 1 에서도**
효과가 난다. 현대 서빙이 전부 4비트 가중치를 쓰는 이유다.

활성값은 INT8 로 둔다. 활성값은 토큰당 한 번만 읽히므로 (가중치와 달리
모델 크기에 비례하지 않는다) 줄여도 이득이 작고, 정확도 손실은 크다.

## 구현

디스크립터 flags bit1 = `FLAG_WGT_INT4`.

MAC 배열은 **그대로 8비트를 받는다.** 니블을 2의 보수로 부호확장해 넣는다.
즉 연산 경로는 전혀 바뀌지 않고 메모리 경로만 바뀐다.

```systemverilog
localparam int NIB_W  = KSTEP_W / 2;   // INT4 K-step = N 니블
localparam int W4PW   = KPW * 2;       // 워드에 두 배로 들어간다

wire [NIB_W-1:0] w4_nibbles = wgt_word[w4_sub_q*NIB_W +: NIB_W];
for (nb = 0; nb < N; nb++)
  assign wgt_rdata_i4[8*nb +: 8] =
    {{4{w4_nibbles[4*nb + 3]}}, w4_nibbles[4*nb +: 4]};
```

`KPW >= 1` 이므로 `W4PW >= 2` 가 항상 성립하고, 주소·부분워드 분할이
비트 슬라이싱만으로 끝난다. 가중치 요청 길이는 따로 (`wgt_len_r`) 센다.

### 포맷은 가중치의 속성이다

INT4 여부는 디스크립터가 아니라 **적재된 가중치**에 딸린다.
weight-stationary 로 건너뛴 디스크립터가 flags 에 INT4 를 안 적어도,
상주 가중치가 INT4 면 INT4 로 읽어야 한다. 그래서 `w4_of_wbank[]` 로
가중치 뱅크마다 보관하고, 연산은 `wgt_bank_of[cm_bank]` 가 가리키는
뱅크의 포맷을 쓴다. `test_int4_resident_across_descriptors` 가 이것을
단언한다 (첫 개만 INT4 로 적재, 나머지는 KEEP 만).

### 구현 중 잡은 범위 버그

`rd_k_mux[W4PW_W +: BADDR_W]` 로 쓰면 범위를 넘는다. N=16/RD=128 에서
`rd_k_mux` 는 8비트인데 `BADDR_W` 도 8 이라 `[8:1]` 이 된다. Verilator
가 `SELRANGE` 로 잡았다. 시프트 후 하위 `BADDR_W` 비트를 취하는 형태로
바꿨다 — 폭에 무관하게 맞고, `Kt <= MAX_KT` 이므로 `k/W4PW` 가
`BANK_DEPTH` 를 넘지 않는다.

## 측정

두 구성(N=16/128비트, N=32/256비트) 모두 동일하게 나왔다.

```
Kt=64  활성값 64 비트 공통
       가중치 INT8 64 → INT4 32 비트     (정확히 절반)
       전체 읽기 128 → 96 비트           (1.33× 절감)
       결과는 INT8 판과 완전히 동일
```

전체가 1.33× 인 것은 활성값이 그대로이기 때문이다. **가중치만 보면
정확히 2×** 이고, LLM 디코드는 가중치가 트래픽의 거의 전부라 실효 이득이
2× 에 가깝다 (활성값은 배치 1 에서 레이어당 수 KB, 가중치는 수백 MB).

## 테스트가 잡도록 만든 것

INT4 는 조용히 틀리기 쉬운 두 지점이 있다.

1. **부호확장.** INT4 는 [-8, 7] 이다. `0xF` 는 −1 이어야 하고 15 가
   되면 안 된다. 테스트가 `assert (B < 0).any()` 로 **음수 가중치를
   강제한다** — 전부 양수면 부호확장 버그가 통과한다.
2. **니블 순서.** 바이트 하나에 K 가 아니라 **열(column)** 이 연속한 두
   값이 들어간다. 하위 니블이 낮은 열이다. 틀리면 짝/홀 열에서만 틀린다.

둘 다 numpy 대조로 잡힌다. Kt=3 (홀수, 워드 경계에 걸침) 도 포함한다.

# 8단계: 확장 곡선과 성능 모델

## 타일 확장 — 측정값

| TILE_N | RD/WR | Kt | 사이클/op | MAC/사이클 | INT8 OPS/사이클 | 가동률 |
|---:|---|---:|---:|---:|---:|---:|
| 16 | 128/128 | 64 | 70 | 234 | 468 | 91.4% |
| 32 | 256/256 | 128 | 134 | 978 | 1,956 | 95.5% |
| 64 | 512/512 | 256 | 262 | **4,002** | **8,004** | **97.7%** |

N 을 2배 할 때마다 **4.18× / 4.09×**, 가동률은 **단조 증가** (91.4 → 95.5
→ 97.7%). 가동률이 오르는 이유는 Kt 가 같이 커져 디스크립터당 고정
오버헤드(상태 전이 6 사이클)가 더 잘 분산되기 때문이다.

이 곡선은 산술 강도가 N 에 비례한다는 예측과 정확히 맞는다.

## 성능 모델 (`tools/perf_model.py`)

모든 숫자에 출처 태그를 붙인 재현 가능한 모델이다.

```
MEASURED  이 저장소의 시뮬레이션/합성. 재현 명령이 주석에 있다.
SOURCED   외부 공개 자료. 출처를 적는다.
ASSUMED   측정하지 않은 값. **동작 주파수가 여기 있다.**
DERIVED   위 값들로 계산한 값.
```

`tests/test_perf_model.py` 가 모델의 모든 구성이 측정 기록에 묶여
있는지, 유도 식이 맞는지, 그리고 **주파수가 가정값임을 밝히는 주석이
남아 있는지**까지 단언한다.

### 결론 1 — 연산 격차와 대역폭 격차는 다르다

| 항목 | 이 설계 (N=32, 300MHz 가정) | H200 | 격차 |
|---|---:|---:|---:|
| INT8 피크 | 0.59 TOPS | 1,979 TOPS | 3,372× |
| 메모리 대역폭 | 25.6 GB/s | 4,800 GB/s | **188×** |
| 메모리 용량 | 16 GB | 141 GB | 8.8× |

### 결론 2 — LLM 디코드에서는 연산 격차가 나타나지 않는다

디코드는 토큰마다 가중치 전체를 한 번 읽는다. **양쪽 다 메모리에
묶이므로** 실효 격차는 대역폭비다.

```
7B, 배치 1       가중치     토큰/s    묶는 쪽
이 설계 INT8      7.0 GB      3.7     메모리
이 설계 INT4      3.5 GB      7.3     메모리
H200    INT4      3.5 GB  1,371.4     메모리
                           → 188×  (= 대역폭비, 연산비 아님)
```

**연산 격차 3,372× 는 이 워크로드에서 한 번도 드러나지 않는다.**
INT4 가 토큰 속도를 정확히 두 배로 만드는 것도 같은 이유다.

### 결론 3 — 배치는 메모리 한계를 밀어올리고 연산 한계는 그대로 둔다

이 설계, 7B INT4, N=32, 300MHz 가정:

| 배치 | 메모리 한계 | 연산 한계 | 실제 | 묶는 쪽 |
|---:|---:|---:|---:|---|
| 1 | 7.3 | 41.9 | 7.3 | 메모리 |
| 4 | 29.3 | 41.9 | 29.3 | 메모리 |
| **8** | 58.5 | 41.9 | **41.9** | **연산** |
| 32 | 234.1 | 41.9 | 41.9 | 연산 |

**배치 8 이 이 칩의 균형점이다.** 그 뒤로는 MAC 을 늘려야 한다 — 그래서
7단계의 타일 확장이 배치 서빙에 의미가 있다. N=64 (2.40 TOPS) 면 연산
한계가 171 토큰/s 로 올라가 배치 24 까지 메모리가 묶는 쪽이 된다.

### 결론 4 — SRAM 상주는 실리콘 양의 문제다

| 장치 | 온칩 SRAM | 대역폭 | 7B INT4 에 필요한 수 |
|---|---:|---:|---:|
| VCK190 | 20.5 MB | 26 GB/s | **171 개** |
| Groq LPU | 230 MB | 80 TB/s (주장) | 15 개 |
| Cerebras WSE-3 | 44 GB | 21 PB/s (주장) | 0.1 개 |

Groq 처럼 DRAM 을 임계 경로에서 빼려면 VCK190 **171 개**가 필요하다.
그것이 '데이터센터급' 과의 진짜 거리다 — **RTL 이 아니라 실리콘 양이다.**

> Groq / Cerebras 대역폭은 벤더 주장이며 독립 벤치마크로 확인하지 못했다.
> VC1902 수치는 AMD 제품 페이지(LUT 899,840 / DSP58 1,968)와 EPCC 문서
> (BRAM 4.2MB + URAM 16.3MB)에서 왔다.

## 이 저장소에서 측정되지 않은 것

정직하게 적어 둔다.

1. **동작 주파수.** 배치·배선을 돌리지 않았다 (이 환경에 Vivado 가 없다).
   위 TOPS 는 전부 가정 주파수 기준이다.
2. **실제 DRAM 지연.** DMA 스텁은 지연 0 으로 응답한다. 실제 메모리는
   더 느리므로 모든 사이클 수가 낙관적 상한이다.
3. **PCIe 디스크립터 비트 위치.** PG343 이 없어 CQ/CC 필드 배치를
   문서와 대조하지 못했다. 보드 첫 기동 때 1순위 의심 지점이다.

# 9단계: 텐서 병렬 클러스터 — 활성값을 한 번만 읽는다

## 왜 코어를 그냥 늘리면 안 되는가

코어를 여러 개 두고 각자 활성값을 따로 읽으면 연산도 읽기 대역폭도 같이
늘어 **산술 강도가 그대로**다. 대역폭에 묶인 설계에서 아무것도 못 번다.

텐서 병렬은 그것을 피한다. 한 레이어의 가중치를 열 방향으로 쪼개 코어마다
다른 조각을 상주시키고, **같은 활성값을 브로드캐스트**한다.

```
  코어 0:  A · W[:, 0:N]      → OUT[:, 0:N]
  코어 1:  A · W[:, N:2N]     → OUT[:, N:2N]
```

Groq / Cerebras 가 모델을 여러 칩에 쪼개는 방식과 같은 원리다.

## 구조 (`rtl/gemm_cluster.sv`)

바깥으로는 읽기 1포트, 쓰기 1포트다. 안에서 이렇게 나눈다.

```
  읽기  ACT 구간: 한 번 요청해 모든 코어에 동시에 넘긴다 (브로드캐스트)
        WGT 구간: 코어 순서대로 하나씩 (고정 우선순위)
  쓰기  코어 순서대로 하나씩
```

코어들은 같은 디스크립터·같은 Kt 로 돌므로 ACT 구간에서 자연히 락스텝이
된다. 브로드캐스트 판정은 "전원이 요청 중이고 주소가 같다" 다 — 가중치
스트라이드가 0 이면 가중치도 자동으로 브로드캐스트된다.

디스크립터에 코어 간 스트라이드를 둔다 (바이트 44..47 가중치, 52..55 출력).

## 측정 1 — 활성값을 한 번만 읽는다

CORES=2, Kt=32, N=32:

```
읽기 요청 3개: 활성값 1개(1,024B) + 가중치 2개(2,048B)
총 3,072B vs 코어별 개별 읽기 4,096B → 1.33× 절감
```

**상주 가중치가 들어가면 디스크립터당 읽기 요청이 1개(활성값)로 떨어진다.**
코어 수와 무관하다.

```
#0 flags=0x00  읽기 요청 3개   ← 가중치 적재 (코어당 1회)
#1 flags=0x01  읽기 요청 1개   ← 활성값만
#2 flags=0x01  읽기 요청 1개
#3 flags=0x01  읽기 요청 1개
```

## 측정 2 — 처리량

| CORES | TILE_N | RD/WR | Kt | 사이클/op | MAC/사이클 | 가동률 | 묶는 쪽 |
|---:|---:|---|---:|---:|---:|---:|---|
| 1 | 32 | 256/256 | 128 | 134 | 978 | 95.5% | 연산 |
| 2 | 32 | 256/256 | 256 | 262 | **2,001** | **97.7%** | 연산 |
| 4 | 32 | 256/**256** | 256 | 588.5 | 1,782 | 43.5% | **쓰기** |
| 4 | 32 | 256/**512** | 256 | 262 | **4,002** | **97.7%** | 연산 |

코어 수에 **선형**이다 (978 → 2,001 → 4,002).

CORES=4 를 256비트 쓰기로 돌리면 가동률이 43.5% 로 떨어진다. 출력량은
코어 수에 비례하는데(코어마다 자기 조각을 쓴다) 연산은 코어당 Kt 사이클
이므로, 균형 조건은

```
Kt = CORES · N² · 4 / (WR_DATA_W/8)
```

이고 CORES=4 / N=32 / 256비트면 Kt=512 가 필요한데 MAX_KT=256 이다.
쓰기를 512비트로 올리면 균형이 돌아온다.

그때 간격이 `[135, 1290, 258]` 로 **주기적으로** 흔들렸다. 쓰기가 직렬화
되며 코어들이 번갈아 기다리기 때문이다. 테스트 단언을 "간격이 일정" 에서
"간격이 코어 수 이하의 주기로 반복" 으로 바꿨다 — 주기성이 깨지면 중재가
불공정하거나 교착에 가깝다는 뜻이고, 그것이 실제로 지켜야 할 성질이다.

## 가장 중요한 결과 — 클러스터가 단일 큰 타일보다 유리하다

같은 MAC 수, 같은 처리량(4,002 MAC/사이클)인 두 구성:

| 구성 | MAC | 활성값 바이트 | 산술 강도 |
|---|---:|---:|---:|
| 단일 64×64 | 1,048,576 | 16,384 | 64 MAC/B |
| **4코어 32×32** | 1,048,576 | **8,192** | **128 MAC/B** |

**클러스터가 읽기 대역폭을 절반만 쓴다.** 브로드캐스트 덕이다.

일반화하면, 코어 C 개의 N×N 클러스터는

```
MAC       = C · N² · Kt
활성값    = Kt · N          (브로드캐스트 — C 와 무관)
산술 강도 = C · N  MAC/B
```

같은 MAC 수의 단일 타일은 한 변이 `N√C` 이므로 강도가 `N√C` 다. 즉
**클러스터가 √C 배 유리하다.** C=4 면 2배, C=16 면 4배다.

이것이 "코어를 늘리는 것" 과 "타일을 키우는 것" 중 어느 쪽을 택할지에
대한 답이다 — **대역폭이 묶는 쪽이면 코어를 늘려라.**

## 그 과정에서 찾은 버그 — 다섯 번째

연속 스트림에서 CORES≥2 가 틀렸다. 디스크립터 하나씩 보내면 정상이었다.

처음 추측은 `done` 집계였다. 쓰기가 직렬화되므로 코어 0 이 먼저 끝나고,
하나의 카운터로 모으면 **자기 완료 두 개**로 CORES 개를 채울 수 있다.
그것도 실제 버그여서 코어별 완료 카운터로 고쳤다. 하지만 증상이 그대로
였다 — **추측으로 두 번 고치려 하지 않고 계측했다.**

쓰기 요청 주소를 전부 기록하니 즉시 드러났다.

```
발행된 out_addr: 0x200000, 0x240000            ← 2개뿐
실제 쓰기 주소:  0x200000, 0x201000, 0x240000, 0x241000  ← 4개뿐
완료 펄스:       16개                          ← 겉보기 정상
```

디스크립터 16개를 흘렸는데 주소가 2개에서 멈췄다.

원인: **각 코어는 자기 `cmd_ready` 로 수락한다.** `cmd_ready_all` 로
AND 해서 ctrl_fsm 에 돌려주기만 하고 `cmd_valid` 는 그대로 넘겼더니,
먼저 준비된 코어가 바로 받아 버렸다. ctrl_fsm 은 `ST_DISPATCH` 에서
`cmd_ready_all` 을 기다리며 `cmd_valid` 를 계속 세워 두는데, 그 사이
먼저 받은 코어가 일을 끝내고 `L_IDLE` 로 돌아오면 **같은 디스크립터를
또 받는다.**

수정은 valid 쪽을 게이트하는 것이다.

```systemverilog
wire cmd_valid_gated = cmd_valid_ctrl & cmd_ready_all;
```

코어의 `cmd_ready` 는 `cmd_valid` 에 의존하지 않으므로(`L_IDLE` 상태와
뱅크 여유만 본다) 조합 루프가 없다.

> **락스텝은 ready 를 AND 하는 것으로 성립하지 않는다. valid 를 게이트해야
> 한다.** 다중 소비자 핸드셰이크의 일반적인 함정이고, 이 저장소에서 찾은
> 다섯 번째 조용한 버그다. 앞의 넷과 공통점도 같다 — 단일 트랜잭션만
> 테스트하면 안 드러난다.

`COCOTB_SIM` 아래에 네 가지 가정을 `$fatal` 로 단언해 뒀다: 코어들이
`rd_data_ready` 를 상시 1 로 두는지, 브로드캐스트 중 요청자가 사라지지
않는지, 코어들이 받은 디스크립터 수가 같은지, 완료 스큐가 카운터 폭을
넘지 않는지.

# 10단계: 실제 레이어 모양 — K 분할 누산과 호스트 타일러

여기까지는 디스크립터 하나, 타일 하나를 빠르게 만드는 일이었다. 이
단계에서 **임의 크기 행렬곱**을 돌린다.

## 공백 1: 축소 차원이 MAX_KT 로 막혀 있었다

디스크립터 하나의 축소 차원은 `MAX_KT`(256)다. 실제 LLM 레이어는
K=4096 이다. 쪼개 누산하지 못하면 이 가속기는 실제 레이어를 못 돌린다.

flags bit2 `FLAG_ACC_KEEP` / bit3 `FLAG_NO_WB` 를 넣었다.

```
조각 0        acc_keep=0  no_wb=1    누산기 클리어, 쓰기 없음
조각 1..n-2   acc_keep=1  no_wb=1    이어받고 쓰기 없음
조각 n-1      acc_keep=1  no_wb=0    이어받고 쓰기
```

`C_CLR` 에서 `mac_acc_clr = ~ak_cm` 로 바꾸고, `C_LATCH` 에서 `nw_cm`
이면 쓰기 FSM 을 기다리지 않고 통과한다. 중간 조각은 `acc_out_lat` 을
건드리지 않는다 — 앞 디스크립터의 쓰기가 진행 중일 수 있다. 쓰기가
없으니 완료 펄스도 연산 쪽에서 낸다 (`cm_pass`).

플래그는 활성값 뱅크마다 보관한다 (`ak_bank[]`, `nw_bank[]`) — 연산 FSM
이 쓰는 값이고, 로드보다 늦게 실행되기 때문이다.

### 측정

```
K=64  chunk=32/16/8/7  →  2/4/8/10 조각   전부 쪼개지 않은 결과와 일치
                          중간 조각 쓰기 0 비트
K=1024 (MAX_KT 의 4배)  4 조각            일치, 최대 누산값 508,820
K 분할 + weight-stationary 동시           가중치 적재 1회, 일치
```

## 공백 2: 호스트가 순서를 알아야 한다

RTL 의 weight-stationary 는 **호스트가 그 순서로 내보낼 때만** 값어치가
있다. `tools/gemm_tiler.py` 가 (M, K, N) 을 디스크립터 수열로 쪼갠다.

### 전략이 두 개인 이유 — 누산기가 한 벌이다

| 조건 | 루프 순서 | 가중치 재사용 |
|---|---|---|
| K ≤ max_kt | `for jb: for ib:` | **있다** (밴드 고정) |
| K > max_kt | `for ib: for jb: for kb:` | **없다** |

K 분할은 한 (ib, jb) 의 부분합이 누산기에 살아 있어야 하므로 `kb` 가
가장 안쪽이어야 한다. 그러면 `ib` 를 안쪽에 둘 수 없어 가중치 재사용이
사라진다. DRAM 누산(read-modify-write)이 있으면 둘 다 되지만 RTL 에 없다.

**실제 레이어는 `max_kt` 를 K 이상으로 잡으면 첫 경로로 간다.** K=4096,
T=32, 2코어면 SRAM 1MB 로 VC1902 온칩 20.5MB 안에 넉넉히 들어간다.
`MAX_KT` 를 512/1024 로 올려 lint 와 SRAM 비용을 확인했다.

### 측정 — 실제 Llama-7B 레이어 (T=32, 4코어, INT4)

| 배치 M | 패딩 효율 | WS 순서 | 순서 무시 | 절감 |
|---:|---:|---:|---:|---:|
| 1 | **3.1%** | 35.23 MB | 35.23 MB | 1.00× |
| 32 | 100% | 35.23 MB | 35.23 MB | 1.00× |
| 256 | 100% | 123.99 MB | 281.80 MB | **2.27×** |

(7B ffn up, 4096→11008)

세 가지가 드러난다.

1. **M=1 은 패딩 효율 3.1% = 1/32.** A 가 T 행이므로 단일 토큰 디코드는
   배열의 1/T 만 쓴다. **디코드가 메모리에 묶이는 구조적 이유**가 이것이고,
   8단계 성능 모델의 "배치 8 이 균형점" 과 같은 사실을 다른 각도에서 본
   것이다.
2. **weight-stationary 는 M ≥ 2·T 여야 효과가 난다.** 행 타일이 하나면
   재사용할 상대가 없다. M=32 에서 1.00×, M=256 에서 2.27×.
3. **K > max_kt 면 절감이 사라진다.** 표의 `ffn down`(K=11008 > 4096)이
   1.00× 인 이유다.

## 엔드투엔드 — 실제 행렬곱이 RTL 에서 돈다

`sim/cocotb/test_gemm_e2e.py` 가 타일러의 디스크립터 수열을 **그대로**
클러스터에 밀어 넣는다. 타일러가 RTL 과 다른 가정을 하고 있으면 깨진다.

```
CORES=2 T=32 MAX_KT=256
GEMM M=64 K=128 N=128 → 디스크립터 4개, 가중치 적재 2개
C[64,128] 전체 8,192개 numpy 와 일치
가중치 적재 4 / 재사용 4 — 타일러 예상과 일치
읽기 요청 총 8개 (활성값 4 + 가중치 4)
```

그리고 순서를 거꾸로 돌려 비교했다. **RTL 은 동일하고 순서만 다르다.**

```
밴드 고정 (타일러)   가중치 적재 2회
행 고정 (반대)       가중치 적재 8회
                     → 4.00× 절감
```

## 타일러가 활성값에 대해 말해 주는 것

디스크립터 하나가 읽는 활성값은 코어 수와 무관하다(브로드캐스트). 그런데
코어가 많으면 한 디스크립터가 더 넓은 열 밴드를 덮으므로 **디스크립터
수가 줄고 총 활성값 트래픽이 1/코어수 로 줄어든다.**

```
cores=1  활성값 65,536 B
cores=2         32,768 B
cores=4         16,384 B
```

9단계의 "클러스터가 √C 배 유리하다" 를 호스트 쪽에서 본 같은 사실이다.
`tests/test_gemm_tiler.py` 가 이 반비례를 단언한다.

# 11단계: 실제 DRAM 지연 — 내가 달아 둔 단서를 숫자로

이 문서의 모든 사이클 수에는 단서가 붙어 있었다. **DMA 스텁이 지연 0 으로
응답하므로 낙관적 상한이다.** 실제 DDR4 는 요청 수락에서 첫 데이터까지
수십 사이클이 걸린다. 그 단서를 숫자로 바꿨다.

`dma_stub.py` 에 `rd_latency` 를 넣고 0 / 8 / 24 / 48 사이클로 쓸어 봤다.

## 측정 (TILE_N=16, Kt=64, RD=256비트)

| 읽기 지연 | WS ON (로드 여유) | WS off (로드 병목) |
|---:|---:|---:|
| 0 | 70.0 (기준) | 70.0 (기준) |
| 8 | 70.0 (**0%**) | 83.0 (+18.6%) |
| 24 | 70.0 (**0%**) | 115.0 (+64.3%) |
| 48 | 82.0 (+17.1%) | 163.0 (+132.9%) |

## 두 가지가 나온다

**1. 파이프라인이 24 사이클까지 완전히 흡수한다 (weight-stationary 켠 채).**
지연은 로드 쪽에만 얹히고, 로드 FSM 은 연산 FSM 보다 한 디스크립터
앞서 돌므로 그 여유가 지연을 먹는다. 48 에서 17% 가 새는 것이 흡수 한계다.

**2. weight-stationary 의 값어치는 트래픽 절감만이 아니다 — 지연 내성이다.**
WS 를 끄면 로드가 묶는 쪽이 되고(87.4% 바쁨) 여유가 없어 지연이 그대로
주기에 더해진다. 8 사이클에서 벌써 18.6% 다.

이것은 예상하지 못한 결과였다. 5단계에서 weight-stationary 를 넣은 이유는
DRAM 트래픽을 절반으로 줄이는 것이었는데, 부수 효과로 **설계가 메모리
지연에 둔감해졌다.** 보드에서 처음 드러나면 늦는 종류의 성질이다.

## 쓰기 지연 — 같은 쓸기를 반대쪽에

위 표의 단서 하나는 "`wr_latency` 는 넣어 뒀지만 쓰기 쪽은 아직 쓸어보지
않았다" 였다. 그래서 `dma_stub.py` 의 `run_write` 가 요청 수락 뒤
`wr_latency` 사이클 동안 `wr_data_ready` 를 내리도록 구현하고 — 읽기 쪽
`rd_wait` 카운트다운의 대응물이다 — 같은 네 지점을 쓸었다.

| 쓰기 지연 | 사이클/op | 손실 |
|---:|---:|---:|
| 0 | 70.0 | 기준 |
| 8 | 75.0 | +7.1% |
| 24 | 91.0 | +30.0% |
| 48 | 115.0 | +64.3% |

**읽기와 달리 흡수되지 않는다.** 24 사이클에서 읽기는 0%, 쓰기는 30% 다.
이유는 구조에 있다:

- 로드 FSM 은 이중 버퍼(`bank_full` 핸드오버)로 연산 FSM 과 떨어져 있다.
  그래서 한 디스크립터 앞서 돌 수 있고, 그 여유가 읽기 지연을 먹는다.
- 쓰기 FSM 은 `acc_lat` **단일** 버퍼 하나로 연산 FSM 과 붙어 있다.
  `C_LATCH` 가 `wst == W_IDLE` 을 기다리므로, 쓰기가 늦으면 연산이 선다.
  앞서 돌 여유가 애초에 없다.

8 사이클에서 손실이 8 이 아니라 5 사이클인 것은 `W_REQ` 와 비트 전송의
일부가 겹쳐 먹히기 때문이고, 그게 유일한 흡수분이다.

이 숫자는 **다음 작업의 근거**다. 누산기 이중 버퍼링은 그동안
"97.7% → 100%, 2.3% 벌기" 로만 적혀 있었다. 쓰기 지연을 재고 나니
값어치가 달라진다 — 보드의 쓰기 지연이 24 사이클이면 30% 를 벌고,
48 이면 64% 를 번다. 읽기 쪽에서 weight-stationary 가 지연 내성을
덤으로 준 것과 같은 종류의 이득이다 (이중 버퍼가 지연 내성을 만든다).

> 남은 단서: 48 사이클을 넘는 지연, 그리고 읽기 요청이 겹칠 때의
> 컨트롤러 재정렬은 재지 않았다.

## 그 과정에서 당한 것 — 스텁 두 개가 같은 신호를 구동

처음 측정은 **모든 지연에서 손실 0%** 였다. 파이프라인이 완벽해서가
아니라, `_sweep` 이 지연마다 `start_dma` 를 불러 스텁 네 개를 띄웠고
**지연 0 짜리 첫 스텁이 계속 `rd_data_valid` 를 세우고 있었다.**

그럴듯한 결과였기 때문에 그냥 넘어갈 수 있었다. 의심한 근거는
"WS 를 꺼도 손실 0%" 가 설명이 안 된다는 것이었고, 스텁이 실제로 지연을
넣는지 직접 세는 탐침을 만들어 확인했다 (간격이 설정과 무관하게 1).

이 저장소에서 같은 함정에 세 번째로 당했다. 그래서 **다시 일어날 수
없게 만들었다.**

```python
_ACTIVE: dict[int, "DMAStub"] = {}

def start_dma(dut, ...):
    if id(dut) in _ACTIVE:
        raise RuntimeError("이 dut 에 DMA 스텁이 이미 돌고 있다 ...")
```

중복 기동이 조용한 오측정 대신 즉시 에러가 된다. 설정을 바꾸려면
`.stop()` 을 부른다.

> 교훈은 버그 자체가 아니다. **그럴듯한 측정값이 가장 위험하다.**
> "지연을 넣었는데 손실이 없다" 는 좋은 뉴스였고, 그래서 검증하지 않을
> 유혹이 있었다. 설명되지 않는 좋은 결과는 설명되지 않는 나쁜 결과보다
> 더 의심해야 한다.

## 그 방어 장치가 바로 찾아낸 것

중복 기동을 에러로 만든 직후, **이미 저장소에 있던 두 테스트**가 걸렸다.

```
test_gemm_utilization       run_gemm() 안에서 start_dma  → GEMM 4개 = 스텁 4개
test_gemm_core_throughput   stream() 안에서 start_dma    → Kt 3개 = 스텁 3개
```

둘 다 **발표된 가동률·처리량 숫자를 그 상태에서 측정했다.** 스텁을
테스트당 하나로 고쳤고 둘 다 통과한다.

방어 장치 자체도 한 번 틀렸다. 첫 판은 살아있음 확인이 없어서, cocotb 가
테스트 끝에 코루틴을 죽인 뒤 같은 모듈의 다음 테스트가 정상적으로 다시
띄우는 것까지 막았다 (4개 실패). `_alive()` 로 고쳤다.

## 죽은 파라미터 제거

`gemm_core` 의 `DMA_BEAT_BYTES` 는 본문에서 아무도 읽지 않는다 — 비트
바이트 수는 `RD_DATA_W`/`WR_DATA_W` 에서 유도한다. 선언과 클러스터에서의
전달만 남아 있었다. 제거했다.

# 12단계: 호스트가 쓸 수 있게 — 플래그가 닿지 않던 문제

11단계까지 만든 기능 전부에 공통된 결함이 있었다. **호스트 스택이 그것을
못 썼다.**

```python
def pack_gemm(act_addr, wgt_addr, out_addr, kt) -> bytes:   # flags 없음
def add_gemm(self, act=0, wgt=0, out=0, kt=4, ...)          # flags 없음
```

weight-stationary, INT4, K 분할, 클러스터 스트라이드 — 네 기능이 모두
디스크립터 플래그와 스트라이드 필드로 제어되는데, 호스트 패커에 그 인자가
없었다. 즉 **cocotb 테스트에서만 닿고 실제 호스트 경로에서는 쓸 수 없는
상태**였다. 그리고 `gemm_tiler.py` 는 아무도 쓰지 않았다.

## SSOT 를 세운다

`tools/orbit_mmio_map.py` 에 플래그와 오프셋을 넣었다.

```python
DESC_FLAGS_OFF      = 1
DESC_WGT_STRIDE_OFF = 44
DESC_OUT_STRIDE_OFF = 52

class DescFlag(IntFlag):
    WGT_KEEP = 1 << 0
    WGT_INT4 = 1 << 1
    ACC_KEEP = 1 << 2
    NO_WB    = 1 << 3
```

`gemm_tiler.py` 는 자기 복사본을 들고 있었는데 이것을 가져다 쓰게 바꿨다.
세 곳(RTL / SSOT / 타일러)이 어긋날 수 있던 것이 두 곳이 되고,
`tests/test_orbit_desc_flags.py` 가 RTL 소스를 직접 파싱해 비교한다.

## 주소 계산을 한 곳으로

`MemLayout` 이 활성값/가중치/출력 주소를 계산한다. 중요한 점은
**엔드투엔드 cocotb 테스트가 같은 코드를 쓴다**는 것이다.

```python
layout = MemLayout(shape, cfg, ACT0, WGT0, OUT0)
for item in plan.issue(layout):
    desc = pack_gemm(**item)       # 호스트의 실제 패커
```

테스트가 자기 패커와 자기 주소 계산을 들고 있으면, 바이트 위치가
어긋나도 테스트는 통과한다. 호스트 경로와 같은 코드를 써야 테스트가
호스트를 검증한다. 이제 `test_gemm_e2e.py` 가 깨지면 호스트가 틀린 것이다.

## 모양 단위 API

```python
sched.add_gemm_shape(shape, cfg, act_base, wgt_base, out_base)
```

(M, K, N) 하나를 디스크립터 수열로 쪼개 큐에 넣는다. 순서와 플래그는
타일러가, 주소는 `MemLayout` 이 정한다.

## 검증

`tests/test_orbit_desc_flags.py` 15개:

- `DescFlag` 비트 위치가 `rtl/ctrl_fsm.sv` 의 `FLAG_*` 와 같다 (소스 파싱)
- RTL 이 flags 를 `latched[1]` 에서 읽는다 (소스 파싱)
- `gemm_cluster` 가 스트라이드를 바이트 44..47 / 52..55 에서 읽는다 (소스 파싱)
- 모든 플래그 조합이 라운드트립하고 CRC 가 맞는다
- **flags/stride 바이트를 뒤집으면 CRC 가 깨진다** — 안 깨지면 변조가 통과한다
- 인자를 안 주면 예전과 같은 바이트 (하위 호환)
- 타일러가 SSOT 를 쓴다
- `add_gemm_shape` 가 타일러 계획과 바이트 단위로 일치하는 큐를 만든다

> 교훈: **기능을 만드는 것과 닿게 만드는 것은 다른 일이다.** RTL 측정이
> 전부 통과하고 문서까지 쓴 뒤에도, 실제 호스트 API 에서는 아무것도
> 켤 수 없는 상태였다. 11단계 동안 그것을 몰랐다.

# 부록: BF16 경로는 아직 가속기가 아니다

남은 일을 정리하다 확인한 사실이다. 이 저장소에는 연산 경로가 둘 있는데
**이번 작업 전부가 하나에만 들어갔다.**

| | INT8 `gemm_core` | BF16 `mxu_bf16_128x128` |
|---|---|---|
| DMA 읽기/쓰기 | 있음 | **없음** |
| 피연산자 공급 | DMA → SRAM → MAC | `a_col[0:DIM-1]` 포트로 직접 |
| 3단 파이프라인 / 이중 버퍼링 | 있음 | 없음 |
| weight-stationary / INT4 / K 분할 | 있음 | 없음 |
| 텐서 병렬 | 있음 | 없음 |

`rtl/g3_int_top.sv` 에는 DMA 포트가 없고 주석이 이렇게 적고 있다.

```
//   2. TB drives a_row/b_col via mxu_data_valid
```

**테스트벤치가 피연산자를 먹여 준다.** 즉 BF16 MXU 는 누산 정확도가
검증된 연산 블록이지만, 실제 데이터를 스스로 가져오지 못한다.

이것은 "업데이트를 못 받았다" 가 아니라 **"BF16 쪽에는 `gemm_core` 에
상응하는 것이 없다"** 는 뜻이다. 올리려면 같은 메모리 아키텍처를 가진
`mxu_core` 를 새로 만들어야 하고, 그건 이번 작업 전체에 맞먹는 규모다.

> 1~5단계에서 BF16 PE 를 고정소수점 누산으로 재설계하고 FP32 변환기를
> 공유하게 만든 작업(`spec/pe-fixed-point-redesign.md`)은 유효하다.
> 그것은 연산 블록 안의 일이었다. 바깥의 메모리 경로가 없는 것이다.

# 13단계: 실제 레이어 깊이 — 16비트 길이 필드가 조용히 잘랐다

10단계에서 K 분할을 넣은 이유는 축소 차원이 `MAX_KT` 로 막혀 있었기
때문이다. 그런데 K 분할은 대가가 있다 — 누산기가 한 벌이라 **가중치
재사용을 잃는다** (실제 레이어의 절반에서 2.27× 절감이 사라진다).

그래서 대안을 먼저 따졌다.

| | 방식 | 비용 |
|---|---|---|
| **A** | 누산 SRAM (출력 타일 여러 개의 부분합) | 복잡. RMW 해저드 |
| **B** | `MAX_KT` 를 K 이상으로 | 피연산자 SRAM 만 커짐 |

## 레퍼런스 — Gemmini 는 A 를 쓴다

`ucb-bar/gemmini` 를 받아 `AccumulatorMem.scala` 를 읽었다. 논문 표현대로
**"입력에 가산기가 붙은 듀얼포트 SRAM"** 이다.

```scala
class AccumulatorWriteReq ... {
  val acc = Bool()        // 누산할지 덮어쓸지
}
val pipelined_writes = Reg(Vec(acc_latency, Valid(new AccumulatorWriteReq)))
val oldest_pipelined_write = pipelined_writes(acc_latency-1)
mem.io.wdata := Mux(oldest_pipelined_write.bits.acc, adder_sum,
                    oldest_pipelined_write.bits.data)
```

RMW 를 `acc_latency` 단으로 파이프라인하고, 가산기를 뱅크 간 공유한다
(`AccPipeShared`, `Mux1H`). 그리고 **그들 자신이 미해결 해저드를 TODO 로
남겨 뒀다.**

```
// TODO Do writes in this module work with matrices of size 2? If we try to
// read from an address right after writing to it, then we might not get the
// written data. We might need some kind of cooldown counter ...
```

즉 A 는 정석이지만 공짜가 아니다.

## B 의 비용을 계산했다

```
K= 4096  4코어  2.00 MB
K=11008  4코어  5.38 MB      ← 가장 깊은 7B 레이어 (ffn down)
VC1902 온칩 20.5 MB
```

**들어간다.** 그래서 B 로 가기로 하고 — 계산을 믿지 않고 RTL 로 돌렸다.

## 그러자 터졌다 — 그리고 그게 중요했다

`MAX_KT=4096` 에서 두 테스트가 모두 타임아웃했다. 원인:

**`rd_req_len_bytes` 는 16비트다.** 256비트 읽기에서 한 요청은 최대
65,504바이트(비트 2,047개)까지다.

| Kt | 비트 | 요청 길이 | 16비트로 |
|---:|---:|---:|---|
| 1024 | 32B | 32,768 | OK |
| **2048** | 32B | 65,536 | **0x0000 → 멈춤** |
| 4096 | 32B | 131,072 | 0x0000 → 멈춤 |
| **11008** | 32B | 352,256 | **0x6000 = 24,576 → 조용히 틀림** |

Kt=2048 은 0 이 되어 멈춘다. **Kt=11008 은 24,576바이트라는 그럴듯한
짧은 요청이 되어 틀린 결과를 낸다** — 멈추는 것보다 나쁘다.

실제 LLM 레이어는 K=4096 / 11008 이다. 즉 **"MAX_KT 를 키우면 된다" 는
답은 이 버그 때문에 성립하지 않았고, 그 사실이 SRAM 계산에는 보이지
않았다.** 계산만 믿고 넘어갔으면 보드에서 처음 드러났을 것이다.

## 고친 방법 — 요청 쪼개기

로드 FSM 이 긴 전송을 여러 요청으로 나눈다. 실제 DMA 엔진도 PCIe MPS 와
AXI 4KB 경계 때문에 같은 일을 한다.

```systemverilog
localparam int LEN_W      = 32;   // 길이 카운터 (16비트로 세면 잘림이 되살아난다)
localparam int RD_REQ_MAX = (65535 / RD_BEAT_B) * RD_BEAT_B;

wire [LEN_W-1:0] rd_this_len =
        (rd_left > LEN_W'(RD_REQ_MAX)) ? LEN_W'(RD_REQ_MAX) : rd_left;
```

`rd_data_last` 는 **이 요청의** 마지막 비트이므로, 전체 전송이 끝났는지는
`rd_left` 로 따로 판단해 REQ 로 되돌아간다.

놓치기 쉬운 지점이 하나 있었다. `load_idx` 를 매 REQ 마다 0 으로
되돌리고 있었는데, 쪼개진 두 번째 요청에서 되돌리면 **SRAM 주소가
되감겨 앞 조각을 덮어쓴다.** `phase_begin` 으로 단계의 첫 요청에서만
되돌리게 했다.

쓰기 길이도 16비트이므로 `OUT_BYTES > 65535` 면 합성 시 `$fatal` 한다
(TILE_N=128 이면 65,536 으로 넘친다).

## 측정 — K=4096 단일 디스크립터

```
TILE_N=32  MAX_KT=4096  (피연산자 SRAM 512KB/코어)
읽기 요청 6개 (한 요청 최대 65,504B)
  활성값 3개 요청, 합계 131,072B, 주소 연속
  가중치 3개 요청, 합계 131,072B, 주소 연속
단일 디스크립터 K=4096: 12,435 사이클, 읽기 8,192 비트, 결과 일치
```

그리고 그 깊이에서 weight-stationary 가 그대로 동작한다.

```
#0 적재  읽기 8,192 비트  12,435 사이클
#1 WS    읽기 4,096 비트   8,336 사이클
#2 WS    읽기 4,096 비트   8,336 사이클
```

## 결론 — 누산 SRAM 은 이 타깃에 필요 없다

요청 쪼개기가 들어가고 나니 `MAX_KT` 를 실제 레이어 깊이로 잡을 수 있고,
그러면 **K 분할 없이 가중치 재사용이 전 레이어에서 유지된다.** 7B 급
기준으로 누산 SRAM(A)을 만들 이유가 없다.

A 가 필요해지는 조건은 따로 적어 둔다: K 가 온칩 SRAM 에 담을 수 없을
만큼 깊을 때, 또는 피연산자 SRAM 을 줄여야 할 때다. 지금 타깃은 둘 다
아니다.

> 측정 없이 결정하지 않은 것이 이 단계의 요점이다. SRAM 계산은 B 가
> 충분하다고 말했지만, B 를 막고 있던 것은 SRAM 이 아니라 길이 필드였다.
> 복잡한 A 를 먼저 만들었다면 **필요 없는 모듈을 만들고도 실제 레이어는
> 여전히 안 돌았을 것이다.**

## 두 번째 버그 — 뱅크 주소가 2의 거듭제곱을 가정했다

요청 쪼개기를 넣고 K=4096 은 통과했다. 그런데 **K=11008 에서 재사용
디스크립터(#1)만 틀렸다.** 첫 디스크립터는 맞았다.

그 모양이 원인을 말해 준다 — 첫 디스크립터는 뱅크 0 만 쓴다.

```
BANK_DEPTH = 11008 → BADDR_W = 14
뱅크 1 주소 = {1, idx} = 16,384 .. 27,391
SRAM_DEPTH = 22,016 → 범위 초과
```

`{bank, idx}` 로 이어 붙이면 `BANK_DEPTH` 가 **2의 거듭제곱이어야 한다.**
4096 은 그렇고, 11008 은 아니다. 그리고 실제 LLM 레이어 깊이는 2의
거듭제곱이 아니다 (11008 = 4096 × 2.6875).

```systemverilog
// 전: {bank, idx}
// 후:
function automatic logic [SADDR_W-1:0] bank_addr(
    input logic [BANK_W-1:0]  b,
    input logic [BADDR_W-1:0] idx);
  bank_addr = SADDR_W'(b) * SADDR_W'(BANK_DEPTH) + SADDR_W'(idx);
endfunction
```

`SADDR_W` 도 `BADDR_W + BANK_W` 에서 `$clog2(SRAM_DEPTH)` 로 바꿨다.
BANKS 가 작은 2의 거듭제곱이므로 합성에서는 덧셈 몇 개가 된다.

### 측정 — K=11008 단일 디스크립터

```
읽기 요청 12개 (한 요청 최대 65,504B)
  활성값 6개 요청, 합계 352,256B, 주소 연속
  가중치 6개 요청, 합계 352,256B, 주소 연속
단일 디스크립터 K=11008: 33,177 사이클, 결과 일치

#0 적재  읽기 22,016 비트  33,177 사이클
#1 WS    읽기 11,008 비트  22,163 사이클
#2 WS    읽기 11,008 비트  22,163 사이클
```

### 회귀에서 지키는 방법

`MAX_KT=11008` 은 디스크립터당 3만 사이클이라 회귀에 넣기엔 느리다.
같은 성질을 가진 작은 값을 쓴다 — `MAX_KT=300` 이면 `BADDR_W=9`,
`2^9=512 > 300` 이므로 이어 붙이기가 똑같이 깨진다
(`sim/cocotb/test_odd_depth.py`). 실제 깊이는
`test_real_layer_depth.py` 가 4096 으로 맡는다.

> **이 저장소에서 찾은 여섯 번째와 일곱 번째 조용한 버그다.** 둘 다
> 계산으로는 보이지 않았다. SRAM 용량 계산은 "들어간다" 고 말했지만,
> 막고 있던 것은 길이 필드와 주소 이어 붙이기였다. 그리고 둘 다
> **보드에서 처음 드러날 종류**였다 — 하나는 멈춤, 하나는 두 번째
> 디스크립터부터 틀린 값.
>
> 앞의 다섯 개와 공통점이 또 있다. `MAX_KT=256` (2의 거듭제곱) 과
> 작은 Kt 만 테스트돼 있었다.

# 14단계: BF16 경로에 메모리를 붙였다 — `mxu_core`

부록에 적었듯 이 저장소에는 연산 경로가 둘인데 **하나만 가속기였다.**
`mxu_bf16_128x128` 은 피연산자를 `a_col`/`b_row` 포트 배열로 받고 DMA 가
없었다. `rtl/g3_int_top.sv` 의 주석이 `TB drives a_row/b_col` 이라고
적고 있듯, 테스트벤치가 먹여 줘야 했다.

`rtl/mxu_core.sv` 가 그 공백을 메운다. `gemm_core` (INT8) 의 메모리
아키텍처를 그대로 가져온다 — 3단 FSM, 활성값 2뱅크 이중 버퍼,
weight-stationary, 요청 쪼개기, 곱셈 기반 뱅크 주소.

## INT8 코어와 다른 네 가지

**1. 원소 폭.** BF16 은 16비트다. K-step 하나가 `DIM*16` 비트다
(DIM=16 → 256비트, DIM=32 → 512비트). INT8 은 `DIM*8` 이었다.

**2. MXU 핸드셰이크.** `mac_array` 는 `en` 하나였지만 MXU 는 프로토콜이
있다.

```
C_CLR    acc_clr 한 사이클   (MXU 는 P_IDLE 에서만 받고, 같은 사이클에
                              start 를 받지 않는다 — else-if 다)
C_START  start + k_steps
C_FEED   data_valid 로 Kt 개를 흘린다
C_WAIT   done_pulse
C_LATCH  acc_flat → acc_lat, 쓰기 FSM 기동
```

**3. 피연산자 타이밍.** MXU 안에서 `tile_en` 이 레지스터다.

```systemverilog
P_RUN: if (data_valid) begin
  tile_en <= 1'b1;        // 다음 사이클에 선다
  k_cnt   <= k_cnt + 1;
end
```

즉 타일은 `data_valid` 보다 **한 사이클 뒤**에 피연산자를 먹는다.
동기 SRAM 은 주소를 낸 다음 사이클에 데이터를 내므로, `data_valid` 와
SRAM 주소를 **같은 사이클**에 내면 정확히 맞는다.

> INT8 코어에서 똑같은 지점에 당했다 (3단계). 거기서는 `mac_en` 이 발행
> 3사이클 뒤여서 앞쪽 K-step 을 놓치고 마지막 것을 중복 누산했다.
> 그래서 이 테스트는 Kt 를 1/2/3/8/17/64 로 돌린다 — 타이밍이 어긋나면
> Kt=1 에서는 우연히 맞고 K>1 에서만 틀린다.

**4. 출력.** `DIM*DIM` FP32 다. DIM=16 이면 1,024바이트로 INT8 16×16 과
같고, DIM=32 면 4,096바이트다.

## 측정

| DIM | MAC | RD/WR | Kt | 사이클/op | MAC/사이클 | 가동률 |
|---:|---:|---|---:|---:|---:|---:|
| 16 | 256 | 256/128 | 64 | 71 | 231 | 90.1% |
| 32 | 1,024 | 512/256 | 128 | 135 | 971 | 94.8% |

INT8 코어와 **같은 급**이다 (N=16 에서 70 사이클 / 91.4%, N=32 에서
134 / 95.5%). 1 사이클 차이는 MXU 의 `acc_clr`/`start` 가 분리돼 있어
디스크립터당 한 사이클을 더 쓰기 때문이다.

weight-stationary 와 요청 쪼개기도 그대로 동작한다 (읽기 64 → 32 비트,
Kt=MAX_KT 에서 주소 연속).

## 허용 오차 — 처음 네 테스트가 전부 실패했고 버그가 아니었다

상대 오차 1e-5 로 비교했더니 네 테스트 전부가 1~4 LSB 차이로 실패했다.
원인은 **고정소수점 누산기의 분해능**이었다.

PE 는 FP32 덧셈이 아니라 Kulisch 방식 고정소수점 누산을 쓴다
(`spec/pe-fixed-point-redesign.md`). `bf16_pkg.sv` 의 `ACC_F = 16` 이
소수부 비트 수이므로 누산기 LSB 가 **2⁻¹⁶ = 1.526e-5** 다.

```
got=0.000946045  exp=0.000961125   차이 1.508e-5 = 0.99 LSB
got=1.76462      exp=1.76468       차이 6.0e-5   = 3.93 LSB
```

**상대 오차로 비교하면 안 된다.** 결과가 작을수록 상대 오차가 커진다 —
1e-3 짜리 원소의 1 LSB 오차는 상대 1.5% 다. 올바른 기준은 절대 오차
**≤ Kt × 2^-ACC_F** 이고, 테스트가 `ACC_F` 를 RTL 소스에서 읽는다
(하드코딩하면 설계와 어긋난다).

> 이것은 교환이고 실제 제약이다. 고정소수점 누산은 큰 값에서 파괴적
> 상쇄가 없고 PE 당 2.21배 작지만, **1.5e-5 보다 작은 값을 정확하게
> 표현하지 못한다.** LLM 추론은 정규화 뒤라 보통 괜찮지만, 더 작은 값이
> 필요하면 `ACC_F` 를 키워야 하고 `ACC_W` 도 같이 커진다.

## 그 과정에서 찾은 버그 둘

**1. MXU 가 최소 구성에서 elaborate 되지 않았다.** `TILES=1`
(DIM=TILE_DIM) 이면 `TIL_W = $clog2(1) = 0` 이 되어 폭 0 비트 추출이
생긴다. 타일이 하나면 타일 번호가 필요 없지만 슬라이싱이 폭 0 을
허용하지 않는다. `TIL_W` 를 1 로 올리고 분기를 **generate** 로 바꿨다 —
런타임 `if` 로 쓰면 죽은 쪽도 elaborate 되어 `rd_idx[9]` (8비트 신호)
범위 초과 경고가 난다. 이제 DIM=16/32/64/128 전부 깨끗하다.

DIM=16 (타일 1개) 을 쓸 수 있게 된 것은 시뮬레이션 속도에 크다 —
`mxu_core` 기본 구성이다.

**2. `feed_cnt` 를 `gemm_core` 보다 좁게 만들었다.** `ADDR_W =
$clog2(MAX_KT)` 는 주소 `0..MAX_KT-1` 을 표현하는 폭이고, `Kt = MAX_KT`
까지 **세려면** 한 비트 더 필요하다. 8비트로 두면 `feed_cnt < 256` 이
항상 참이 되어 K-step 을 영원히 흘린다.

`Kt = MAX_KT` 에서만 드러난다. 다른 세 테스트는 Kt ≤ 128 이라 통과했고,
요청 쪼개기 테스트가 `Kt = MAX_KT` 를 쓰기 때문에 잡혔다.
`gemm_core` 는 이 카운터를 32비트로 뒀는데 내가 좁혔다.

## 아직 안 한 것

`FP32_OUT=1` (조합 `acc_flat`) 경로만 쓴다. `STREAM_RD=1` 은 타일당
변환기 하나를 공유해 타일당 143,394 셀을 아끼지만(20.8%), `rd_fp32` 가
사이클당 하나씩 나오므로 쓰기가 `OUT_BEATS` 대신 `ACCS` 사이클이 된다.
DIM=16 이면 64 → 256 사이클이다. 그 교환을 재는 것이 다음 일이고,
먼저 이 경로가 맞아야 했다.

텐서 병렬 클러스터(`gemm_cluster`)도 BF16 쪽에는 없다.
