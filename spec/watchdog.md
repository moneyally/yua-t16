# spec/watchdog.md — 워치독 타이머 (SSOT)

버전 0.1 (2026-09-11).

이 문서가 `WDOG_CTRL` 비트 배치의 **유일한 출처**다.
`rtl/wdog_timer.sv`, `rtl/reg_top.sv`, `tools/orbit_mmio_map.py`, `tb/tb_wdog_timer.py`
가 전부 이것을 따른다. 어긋나면 이 문서가 맞고 코드가 틀린 것이다.

---

## 0. 왜 있는가

지금까지 `WDOG_CTRL` 은 **레지스터일 뿐이었다** — 값을 받아 두고 아무 일도 하지
않았다 (`rtl/reg_top.sv` 의 "Proto-A stub: register only, no actual timer").
유일하게 동작하던 것은 bit[31] 테스트 주입이다.

보드에서 이게 왜 문제인가: `DELTA_STEP` 이 멈추면 (디스크립터 FSM 이 응답 없는
메모리를 기다리거나, 내가 아직 못 찾은 버그로) **호스트가 할 수 있는 일이 없다.**
`SW_RESET` 은 호스트가 레지스터를 쓸 수 있을 때만 듣는다. 칩 자신이 스스로
빠져나올 길이 하나는 있어야 한다. 그게 워치독이다.

`reset_seq` 는 이미 `wdog_reset` 입력과 `BOOT_CAUSE[1]=WDOG` 래치를 갖고 있다.
**없는 것은 타이머 하나뿐이다.**

---

## 1. 레지스터

`WDOG_CTRL` = `0x8030_1014`, RW.

| 비트 | 이름 | 방향 | 뜻 |
|---|---|---|---|
| [0] | `EN` | RW | 1 = 타이머 동작. 0 = 정지 **및 카운터 리로드** |
| [1] | `KICK` | W1P | 쓰기에 1 이면 카운터를 리로드한다. **저장되지 않는다** (읽으면 항상 0) |
| [7:2] | — | RO0 | 예약. 0 을 쓴다 |
| [23:8] | `PERIOD` | RW | 타임아웃 = `(PERIOD + 1) × 1024` 사이클 |
| [30:24] | — | RO0 | 예약 |
| [31] | `TEST_FIRE` | W1P | 쓰기에 1 이면 **즉시** `wdog_reset` 1펄스. 저장되지 않는다 |

읽으면 `{8'b0, PERIOD, 6'b0, 1'b0, EN}` 이 나온다 — **KICK 과 TEST_FIRE 는 0 으로
읽힌다.** 쓰기 펄스이지 상태가 아니기 때문이다.

`TEST_FIRE` 는 **기존 동작 그대로다.** `EN` 과 무관하게 먹는다. 이미 이것에
의존하는 테스트가 있다 (`tb/tb_reset_seq*`) — 깨뜨리지 않는다.

### 왜 1024 사이클 단위인가

100MHz 에서 `PERIOD=0` 은 10.24µs, `PERIOD=0xFFFF` 는 0.67초다.
토큰 하나가 126사이클이므로 가장 짧은 창도 토큰 8개 분량이다 — 정상 동작을
자르지 않으면서, 멈춘 칩을 1초 안에 되살린다.

1024 는 `rtl/wdog_timer.sv` 의 `PRESCALE_LOG2=10` 파라미터다.
**테스트에서 이 값을 바꾸지 않는다** — 바꾸면 보드에서 도는 것과 다른 회로를
검증하게 된다. 대신 테스트는 `PERIOD` 를 작게 쓴다 (`PERIOD=0` → 1024 사이클,
시뮬레이션 10µs).

## 2. 동작

```
리셋 직후            : EN=0, PERIOD=0, 카운터 = 리로드값
EN=0                 : 카운터를 리로드값으로 유지한다 (세지 않는다)
EN=1                 : 매 사이클 카운터를 1 줄인다
카운터가 0 에 닿으면  : timeout 1펄스 → reset_seq.wdog_reset → BOOT_CAUSE[1]=1
                       그리고 카운터를 리로드한다 (펄스는 1사이클, 연속으로 안 뜬다)
KICK=1 을 쓰면        : 카운터를 리로드한다 (EN 과 무관)
PERIOD 를 쓰면        : 새 값이 **다음 리로드부터** 적용된다. 진행 중인 창은 안 건드린다
```

**왜 PERIOD 쓰기가 즉시 리로드가 아닌가:** 즉시 리로드면 호스트가 `PERIOD` 를
주기적으로 다시 쓰는 것만으로 워치독이 영원히 안 터진다 — 킥을 안 해도.
그건 워치독이 아니다. 창을 다시 여는 방법은 **`KICK` 하나뿐**이어야 한다.

**`EN` 을 0→1 로 켜면 리로드한다.** 켜자마자 옛 카운터 잔값으로 터지면 안 된다.

## 3. 호스트 절차 (`tools/orbit_device.py`)

```python
await dev.wdog_enable(period=99)   # (99+1)×1024 = 102,400 사이클 ≈ 1.02ms @100MHz
...
await dev.wdog_kick()              # 살아 있다고 알린다
...
await dev.wdog_disable()
```

`wdog_enable` 은 **PERIOD 와 EN 을 한 번에 쓴다** (EN=1, KICK=1 을 같이 실어
새 창으로 시작한다). 두 번 나눠 쓰면 그 사이에 옛 PERIOD 로 터질 수 있다.

## 4. 검증

| 무엇 | 어디 |
|---|---|
| 타이머 단독 (리로드·킥·EN·PERIOD 반영 시점·펄스 1사이클) | `tb/tb_wdog_timer.py` |
| 레지스터 필드 디코드 + 읽기값 (KICK/TEST_FIRE 가 0 으로 읽힘) | `tb/tb_g2_ctrl_top_wdog.py` |
| 통합: 킥을 멈추면 리셋되고 `BOOT_CAUSE[1]` 이 선다 | `tb/tb_g2_ctrl_top_wdog.py` W3 |
| **`DELTA_STEP` 한가운데 리셋 → 되살아나서 골든과 비트 일치** | `tb/tb_g2_ctrl_top_wdog.py` W7 |
| 잘린 디스크립터가 **유령 `DESC_DONE` 을 안 남긴다** | `tb/tb_g2_ctrl_top_wdog.py` W8 |
| 레지스터맵 SSOT 일치 | `tests/test_mmio_map.py` |

**기대값의 출처는 이 문서다.** 계산이 없는 블록이라 `sim/golden/` 대응이 없다 —
`tb/tb_wdog_timer.py` 는 이 절의 표를 파이썬으로 다시 적은 모델과 비교한다.

## 5. 왜 "동작 중 리셋" 을 따로 보는가 (W7·W8)

W1~W6 은 칩이 **놀고 있을 때** 워치독을 본다. 그런데 워치독이 실제로 터지는 때는
**칩이 멈췄을 때**, 즉 `DELTA_STEP` 한가운데다. 놀 때만 확인하고 끝내면,
정작 필요한 순간의 동작은 아무도 안 본 것이 된다.

W7 은 `DR1_STATUS[0]`(busy)이 선 것을 **확인한 뒤** 리셋을 쏘고, 풀린 다음
호스트 스택으로 `DELTA_INIT` + `DELTA_STEP` 을 돌려 골든과 비트 비교한다.
"몇 사이클쯤이면 한가운데겠지" 로 세지 않는다 — 디스크립터 디코드가 길어지는 날
리셋이 STEP 시작 전에 떨어지고, 테스트는 통과하는데 보려던 것은 안 보게 된다.

W8 은 잘린 디스크립터가 `DESC_DONE` 을 올리지 않는지 본다. `docs/BUGS.md` BUG-001
과 같은 성격이다: 끝나지 않은 디스크립터의 완료 IRQ 는 호스트가 **없는 결과를
읽으러 가게** 만든다.
